# 开源发布设计(2026-11-04)

状态:设计稿,未动手。依据:对 CubeSandbox 的调研、对本仓库的扫描(下文"现状扫描")、与用户的几轮讨论。

## 1. 已定的前提

- 项目是用户**个人的**,不涉及公司法务与审批。
- 三个目标都要:社区贡献、知名度、商业客户。它们对"现在能发什么"的要求不同,见 §6。
- 范围:**沙箱云和 agent 层都开源**,保留在同一仓库,agent 层后续继续做特性。前提是两层的依赖方向清楚(§3)。
- **自研 VMM 暂缓。** 它需要的系统权限和现在的 Firecracker 一样:能访问 `/dev/kvm`(盒子上用户不在 kvm 组,节点跑在容器里),联网要 `CAP_NET_ADMIN`,懒加载内存要 userfaultfd(见 D81)。权限不是障碍,障碍是工程量:设备模型、快照、vsock、balloon 都要重写。要做也该先看 rust-vmm 的现成部件或 Cloud Hypervisor,不是现在。

## 2. 参照物:CubeSandbox

Apache 2.0,基于自研 RustVMM + KVM,兼容 E2B SDK;组件有 API、调度、代理、eBPF 虚拟交换机、带凭据注入与审计的出口网关;有 CONTRIBUTING、双语 README、Discord、贡献者计划。冷启动"低于 60 ms"是厂商自报,未经独立验证。公开资料里**没看到**"所有者审批放宽出口"和"检查点/回滚/fork 作为一等能力"的同等描述(未逐项核对)。我们没有 eBPF 交换机,也没有自研 VMM。

差异化只在有证据的地方讲:检查点回滚 fork(有实测,D81)、出口审批与哈希链审计(有实测,D78/D80)、自己的开发回路在沙箱里跑的记录(dogfood 文档)。**不写没测过的性能数字**,发布基线脚本让别人自己跑。

## 3. 范围与分层

单仓库,三层,依赖只能向下:

| 层 | 目录 | 说明 |
|---|---|---|
| 沙箱云 | `cp` `node` `guest` `sdk` `console` `deploy` `recipes` | 核心,对外承诺 |
| 接入与评测 | `intake` `eval` | 用沙箱云的 HTTP API/SDK |
| agent 层 | `aios` `web` | 同上 |

**验收**:加一条 CI 检查,上两层只能 import 公开 SDK 或走 HTTP,不得读沙箱云内部模块。**这条目前没验证过**,先扫一遍再决定要不要改代码。

体量:`eval` 约 11.6 万行(绝大部分是任务集数据与评测代码),`cp` 1.2 万,`node` 5 千。任务集里有第三方内容,见 §4。

## 5. 历史怎么处理

选项:①保留历史,用 `git filter-repo` 剔除大二进制并改写作者邮箱;②**公开仓库从一个干净的初始提交开始**,私有仓库保留完整历史。

推荐②。决策记录(`docs/decisions.md` D1–D81)已经承载了"为什么这样做",社区更需要干净的仓库;①的风险是漏剔除某个提交里的东西,且 `filter-repo` 改写后哈希全变,内部的提交引用(CHANGELOG/文档里的 `a09dad9` 之类)会失效,要一起改。

## 6. 三个目标各自要什么

- **社区贡献**:外人能在没有我们的盒子的情况下装起来、跑通测试、读懂代码。要:一条命令部署、公开 CI、CONTRIBUTING、`good first issue`、英文文档。
- **知名度**:要有一个值得传播的点和能复现的证据。要:基线对比脚本与结果、演示、清楚的定位;**名字**(见 §9)。
- **商业客户**:要信任。要:`SECURITY.md` 和披露流程、威胁模型公开(已有 `013`)、诚实说明"尚未经第三方安全审计"、托管版或支持的路径、不会被改许可证的承诺。

## 8. 要在发布时讲清楚的局限

单台共享机实测;没有对外基线;没有第三方安全审计;多节点只做过功能验证,没做压力;uffd 未启用(D81)。这些写在 README 的"状态"一节,不藏。

## 9. 需要用户定的事

1. **项目名。** 仓库现在叫 Cairn。我印象里已有同名的、关注度不低的 LLM agent 操作系统项目(agiresearch/Cairn),**我没有核对,请你自己搜一下**。重名会影响被找到和商标,建议发布前改名。
2. **托管位置与账号:** GitHub 个人账号还是新建组织。
3. **贡献协议:** DCO(轻)还是 CLA。若以后想做"开源核心 + 闭源增值",CLA 或从一开始就保留重新授权的权利更省事;纯 Apache 加托管服务则 DCO 够用。**这个要在收到第一个外部贡献之前定。**
4. **商业模式的大方向:** 全部开源、靠托管与支持,还是开源核心加闭源的多租户/计费。影响哪些代码现在可以发。
5. **发布节奏:** 是先做 P0–P2 小范围试用,还是一次性公开。
