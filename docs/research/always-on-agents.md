# Always-on agent 怎样被使用:Lee Robinson 的 CS146S 讲座与 Grok Bot

Lee Robinson(Cursor → SpaceX)2026-10-08 在 Stanford CS146S 讲《How always-on agents work》,讲的是 Grok Bot 一类"一直在线的个人 agent"怎样工作。本文不是讲座的转录(没有公开文字稿;以下来自讲者的章节列表和几篇二手整理,出处见末尾),而是把它按**用户使用的过程**重排,再对照我们现在做的东西,看哪里是按架构而不是按使用来做的。

## 一、用户经历的过程

讲座和 Grok Bot 的产品把用户的经历分成这几段。每段写清:用户做什么、agent 做什么、什么时候用户会被打扰。

| 阶段 | 用户做什么 | agent 做什么 | 用户被打扰吗 |
| --- | --- | --- | --- |
| 1 拥有 | 得到一个有"岗位"的 Bot(销售外联、报销、复现 bug、幕僚长……),它有自己的云端电脑(桌面、文件系统、终端、浏览器) | 什么也不做,睡着 | 否 |
| 2 接入 | 把它接进自己已经在用的地方:Slack、邮件、日历、GitHub;让它登录自己的工具 | 以自己的身份出现在那些地方 | 否 |
| 3 交代 | 在手机或桌面上跟它说一句话,或在群里 @ 它;换设备接着同一段对话 | 确认接到,在云端电脑上开始做 | 一次确认 |
| 4 走开 | 合上笔记本 | 继续做;需要机器时把电脑唤醒,空闲两分钟就睡,下一个事件再醒 | 否 |
| 5 被找 | 只有在**做完、卡住、要做决定**的时候收到消息;不可逆的动作(发邮件、付款)先看到草稿,确认了才发 | 唯一可见的输出是 `SendToUser`;其余模型文本都不给用户看;一轮可以悄悄结束 | 只在这三种情况 |
| 6 纠正 | 在它干活时插一句"不对,周四再做" | 一对一消息优先于排队的工作,可以打断当前一轮;连发的几条合并理解 | 否(是用户主动) |
| 7 教它例行 | 做一遍给它看,或说"以后每天早上……";它存成 routine | 按时或按事件自己醒来做;新 routine 要用户批准 | 批准一次 |
| 8 它自己来活 | 什么都不做 | 被事件叫醒:Slack 消息、邮件、PR 线程、定时器、后台任务完成;重新接上掉线的线程,催停滞的交接,有时先于用户发现该做的事 | 只在做完 / 卡住 / 要决定时 |
| 9 它记得你 | 偶尔纠正它 | 四层记忆:稳定偏好(随时在上下文里,≤100 条、4000 字)、带日期的日志(取最相关的 30 条)、当前工作笔记、文件与证据;每轮后更新;记忆是信息不是指令 | 否 |
| 10 多个 Bot | 给不同岗位开不同 Bot;团队共用 | Bot 之间可以在一个线程里传活、交接所有权;"幕僚长"协调专家 | 同上 |

两条产品原则贯穿全程:**同事而不是工具**——"你大概一天只需要一次状态汇报,取决于任务";**尽量少做产品**(build as little product as possible)、为下一代模型而不是当前模型建系统。

## 二、支撑它的系统(讲座的技术部分,按上面的阶段对应)

- 3/4 **服务端循环**:模型 + 工具的循环跑在服务器上,每一步都存下来;客户端只显示进度。进程不常驻:空闲两分钟即停,下一个事件带着保存的状态把它拉起来。
- 4 **可替换的电脑**:每个用户一台 Firecracker microVM,该用户的各个 agent 共用,各自有虚拟显示器和 Chrome;空闲时把文件同步到对象存储、给内存和磁盘做快照、停机;需要电脑的工具调用时恢复快照。
- 3–8 **事件、队列、路由**:触发源有用户消息、Slack、群消息、routine、webhook、helper 结果、check-in;路由器去重并选中会话;每个会话一个队列,同一时刻只跑一轮;连发合并;一对一消息可以打断。
- 4/8 **持久工作流**(Temporal):每步记录,另一台服务器可以接着跑;定时器、取消、健康检查内置;每个 helper 一个工作流。外部动作必须幂等,否则重试会发两次邮件。
- 5 **输出边界**:`SendToUser` 是唯一出口;客户端按唯一 ID 存消息,重试不重复;变化通知只说"去拉新数据",不带内容,客户端按序号应用、发现缺口就重载。
- 5 **授权**:邮件和 webhook 内容标为不可信;一个独立模型审查有风险的动作,拦下就向用户要批准,15 秒没回答保持拦截;不可逆的发送要先草稿后确认;新 routine 要批准;密钥在模型之外的环境变量里。
- 全程 **上下文工程**:提示按固定顺序拼装(工具定义、系统提示、首条消息在下次摘要前保持不变),历史只在末尾增长;缓存未命中算 bug,每段带哈希定位改动;空闲约 10 分钟且超过 10 万 token 时压缩,缓存还热的时候压;最近的用户可见消息逐字保留;后台工作快要唤醒时跳过压缩。
- 全程 **工具**:名字常驻,描述与 schema 按需加载,每个定义 ≤4000 字,工具集跨轮稳定;选择顺序按成本升序:已有上下文与记忆 → 应用 API → 网页搜索 → 已登录的浏览器 → 完整桌面 → 问用户;连接器坏了要报告而不是绕过去用浏览器;模型反复敲同一种 shell 就把它做成专用工具。
- 8 **helper**:长任务交给 helper,主 agent 给完整任务描述、收回简短报告;computer-use helper 在 1280×800 显示器上做,需要时把控制交还给人;云端编码 helper 在自己的 VM 里,不碰用户的那台。
- 10 **去向**:把为旧模型弱点搭的脚手架拆掉,留下持久状态、去重、证据存储、权限边界;"跑几周几个月"还是假设;每次失败(用错工具、漏掉纠正、重复动作)都变成以后必须通过的评测用例。

## 三、对照我们现在的东西

我们是从架构往上做的:沙箱(003)→ 接单(005)→ 执行(006)→ 评测(007)→ 工作台(008)。拿上面的十个阶段逐段看,有的我们已经有(只是名字不同),有的完全没有:

| 阶段 | 我们有什么 | 缺什么 |
| --- | --- | --- |
| 1 拥有 | Cairn 版本 + 沙箱池;但没有"用户"也没有"我的 agent"这个对象;控制面无鉴权 | 用户体系;每个用户一个 agent(一份记忆、一份策略、一份预算、一池沙箱) |
| 2 接入 | Gitea Source,bot 身份 cairn-bot;策略全局、管理员改 | 用户自己接入渠道(IM、邮件、代码托管);凭据在宿主侧保管、不进沙箱(009 已定) |
| 3 交代 | 工作台发单、Gitea @ 提及;接单回帖确认 | 跨设备同一段对话;对话是中心对象而不是工单 |
| 4 走开 | 接单层常驻,沙箱持久;watchdog | 空闲即睡、需要时恢复快照(003 有 pause/快照,没有空闲策略);派工状态在进程外(intake 的 sqlite 够用,但重启后运行中的派工只能"恢复派工"而不是接着跑) |
| 5 被找 | Report 有 ready/waiting/blocked/failed;回帖发到 Gitea;工作台无通知 | **只在做完/卡住/要决定时说话**的输出纪律(SendToUser 作为唯一出口);推送渠道;不可逆动作的草稿—确认(我们只有 Mandate 的范围,没有按动作的批准) |
| 6 纠正 | inbox 在下一步送到;人的 stop 终止 | 一对一消息优先、能打断当前模型调用;连发合并 |
| 7 教它例行 | 策略里的 schedules(管理员配) | 用户在对话里定 routine,新 routine 要批准;"做一遍给它看"不做 |
| 8 它自己来活 | ci / evaluation / schedule / gitea 四种 Source | 续接掉线线程、催停滞交接(属于 agent 行为,不是接单层) |
| 9 它记得你 | 没有。每张工单从干净克隆开始 | 四层记忆,跨工单、属于用户;每轮后的记忆更新;记忆只是信息 |
| 10 多个 agent | helper 在 harness 里有子 agent 的雏形(004) | 多个 agent 共一个线程、交接所有权;团队 |

还有两处我们和它方向不同、要保留的:

- 它的执行单元是"每个用户一台电脑",我们是"每张工单一台 microVM、一个用户很多台"。我们这样做是为了隔离与并行(003),代价是记忆和凭据不能靠"同一台电脑"自然延续,必须由平台显式提供(第 9 阶段的记忆、第 2 阶段的凭据)。
- 它的 agent 不改自己;我们的 agent(Cairn)在评测下自我改进(007)。对用户而言这应当像应用更新:"你的 agent 更新了,改了什么、在你的任务上好了多少",而不是版本树。

## 四、结论

讲座里没有一处是从"沙箱"或"接单"开始讲的,它从用户的一天开始讲。我们的域模型(002)和工作台(008)都把 Ticket 当中心对象,这是从接单层的视角看世界;用户的视角里中心对象是**和自己的 agent 的一段持续对话**,工单、派工、Mandate 都是对话背后的实现。按使用过程重排产品,需要在 002 之前先写清这十个阶段里我们要做哪些、每段用户看到什么,再让后面的文档对着它改。
