# 实验 1:把开发与 CI 回路搬进沙箱(2026-11-04)

> 状态:**第一轮已做完**(2026-11-04),结果见第 8 节。决定见 D74。
> 前置:[商业化差距](commercialization-gap-2026-11.md)、[自定义模板教程](../guide/tutorials/custom-template.md)。

## 1. 要回答的产品问题

沙箱能不能取代"直接占用共享盒子"来做日常开发和测试?

现在的做法:改完代码 → tar 到盒子 → 在盒子上用 golang 镜像和 Postgres 容器跑测试 → 提交 → 等 CI。盒子上有别人的任务,所以不能压测,测试也只能轻跑。放进沙箱后,测试占用的是沙箱自己的资源配额,隔离、可计量、可回滚。

## 2. 做法

**开发模板 `dev-go`**:在 debian-13 基础镜像和现有 `dev-tools` 层(git、gcc、make、jq、python3 + pytest)之上,加一个 `go-toolchain` 层:

| 内容 | 来源 | 为什么这样拿 |
| --- | --- | --- |
| Go 1.26 | Mac 下载官方 tarball,scp 到盒子,走归档构建 | 盒子访问不到 go.dev 和 GitHub(见 dev-box 记忆) |
| Go 模块缓存(预热) | Mac 上 `go mod download`,打包进层 | 盒子到 proxy.golang.org 不通,离线最稳 |
| PostgreSQL 17 | 盒子能访问 aliyun 镜像,`apt` 装 | 和 `dev-tools` 层同样的路径 |
| `uv` + pytest、jinja2、pyyaml | 同上,wheel 在 Mac 下载 | 跑 Python 测试用 |

准备好后启动 Postgres 并等它就绪,**再提交成模板**:模板带内存,所以新沙箱出生时 Postgres 进程已在。

**每次任务的流程**:`template_key=dev-go` 建沙箱 → 把改动的源码 tar 通过 files API 写入 → `go test ./...`(带 `CAIRN_TEST_PG`)→ 取回结果 → 销毁沙箱。

## 3. 度量(都在沙箱内部或 API 上量,不压测盒子)

| 指标 | 现状基线 | 看什么 |
| --- | --- | --- |
| 从"要跑测试"到"测试开始"的时间 | 手动 tar+scp+启动容器,约几分钟 | 模板热启动 + 写入源码的耗时 |
| 同一套 Go 测试的结果 | 盒子上 golang 容器 + 真实 Postgres | 通过数量一致 |
| 测试墙钟时间 | 盒子上同一套 | 沙箱 2 vCPU / 内存配多少够,不求更快,只求不慢到不能用 |
| 资源计量 | 无 | 控制面用量里这次的 vCPU·s、内存·s,和 `metrics` 曲线 |
| 对共享盒子的影响 | 盒子上多出容器 | 沙箱的 cgroup 峰值,确认没有越过配额 |

## 4. 预期会暴露的问题(这就是做实验的价值)

1. 模板缺什么:例如 `go vet`、`govulncheck`、`golangci-lint` 要不要进模板。
2. 出口策略:测试里 `go mod download` 会不会被拦;要放行哪些域名,还是应该完全离线。
3. 文件同步:源码用 tar 整体写入够不够快,增量同步要不要做。
4. Postgres 随模板快照后,恢复出的进程是否健康(共享内存、监听 socket、时钟跳变)。
5. 沙箱内 Postgres 与测试用的 `CAIRN_TEST_PG` 临时库是否冲突。

## 5. 不做的事

- 不压测、不测并发上限、不比较"沙箱比裸机快多少"。
- 不替换 CI:CI 仍用现有 runner。实验只回答日常开发回路。
- 不把 DeepSeek 密钥放进沙箱。

## 6. 成功与失败的判据

- **成功**:同一份代码,沙箱里的 Go 测试结果与盒子一致;从触发到开跑在 10 秒内;连续用一周没有因沙箱本身出问题的失败。
- **失败也有价值**:如果 Postgres 快照恢复不稳,说明"模板带状态"在有数据库的场景要换做法(如恢复后再初始化),这是对产品的直接反馈。

## 8. 第一轮结果(2026-11-04,盒子上的真实控制面)

做法按上文:`recipes/go-toolchain` 层(Go 1.26.10、预热的模块缓存 448 MiB、PostgreSQL 17.11)叠在 `dev-tools` 层上,提交成模板 `dev-go`(Postgres 已在运行,Go 编译缓存已预热)。脚本 `ops/dogfood-devloop.py`,项目 `dogfood`。

| 指标 | 结果 |
| --- | --- |
| 沙箱出生到 Postgres 可用 | 0.8–1.1 s(Postgres 随快照就在,`pg_isready` 立刻返回 0) |
| 写入源码 + 解包 | 0.06 s + 0.07 s(cp/ 约 470 KiB) |
| 全部 Go 测试(`./...`),冷编译缓存 | 68 s,CPU 128 s |
| 全部 Go 测试,预热缓存 | 11–12 s,CPU 约 15 s;从触发到出结果共 12–13 s |
| 单包(`./internal/tenancy`) | 3–4 s |
| 结果 | 所有包通过;Postgres 日志里有每个测试建的临时库 `t_<hex>`,确认真的用了模板里的 Postgres |

**判据**:结果一致(通过);开跑时间 10 s 内(出生 + 写入约 1 s);"连续一周"还没到,脚本已留在 `ops/`,继续用。

## 9. 这轮暴露的问题

1. **打包层受 `/run` 限制**:`pack` 把整个可写层 tar 到 guest 的 `/run`(内存的一半),1.4 GB 的层在 1 GiB 沙箱里直接 `No space left`。临时办法:`BUILD_MEM=4096`(已加到 `node/build-layer.sh`,并让失败信息可见)。根治要让 guest 把 tar 流式送出,不落 `/run`。
2. **控制面不能删除或替换同名模板**:`POST /builds {kind:commit}` 遇到同名返回 409,而 CP 没有 `DELETE /templates/<名字>`(节点有)。这次我直接调节点删了自己建的模板。该补一个 CP 端点。
3. **guest 没有 `localhost` 解析**:`/etc/hosts` 里缺 `127.0.0.1 localhost`,Postgres 默认监听 `localhost` 起不来。模板里补了,但应当进基础镜像。
4. **模板快照不会缩小**:提交前 `drop_caches` 后 `mem_mib` 仍是 1.6 GiB,出生从 0.14 s 变成 0.6–0.9 s。已释放的页没有被归零,气球 free-page-reporting 没起作用的路径要查。
5. **模板要求请求配置完全一致**:用 `template_key` 建沙箱必须带上相同的 `layers` / `vcpu` / `mem` / `disk`,否则 400。脚本现在先查 `/templates` 再照抄;SDK 应该给个"按模板名建沙箱"的快捷方式。
6. **Go 构建缓存是大头**:冷缓存 68 s,预热后 11 s。预热进模板是这个场景最有价值的一步。

## 11. 实验 2:检查点 + fork(2026-11-04,D77)

**问题**:检查点加 fork,比重做准备工作划算吗?**真实负载**:我们自己的 Go 测试套件;`ops/dogfood-fork.py`。`dev-go` 模板出生,解包源码,打检查点 `ready`(Postgres 在运行、编译缓存预热);先在父沙箱里串行跑完,回滚,再 fork 3 份、每份跑一个包分片。

| 指标 | 预热缓存 | 冷缓存(重建 60.7 s 后打检查点) |
| --- | --- | --- |
| 打检查点 | 1.3 s | 2.9 s |
| 串行跑全套 | 11.7 s | 10.7 s |
| 回滚到检查点 | 3.1 s,状态确实回去(脏文件没了,Postgres 在) | 4.9 s,同样回去 |
| fork 3 份 | 7.2 s(每份约 2.4 s) | 9.7 s(每份约 3.2 s) |
| 3 份并行跑分片 | 11.1 s(最慢的分片) | 11.3 s |
| 并行合计(fork + 最慢分片) | 18.3 s | 21.0 s |
| 隔离 | 一个克隆里写的文件,父和另外两份都看不到 | 同 |

**结论**
1. **把测试套件分片并行,不划算**:`httpapi` 一个包就占 11 s,和串行整套差不多;并行合计 18–21 s,反而比串行 11 s 慢。这个负载上 fork 做不出加速。
2. **从模板扇出,模板出生更便宜**:模板出生每个约 0.7 s,fork 每个 2.4–3.2 s。模板里已有的状态,不该用 fork 去复制。
3. **fork 的价值在"任务做到一半才有的昂贵状态"**:冷缓存时重建要 60.7 s,fork 3 份只要 9.7 s,每份省约 51 s,三份合起来少算两遍重建(CPU 从 3×60 s 到 1×60 s)。
4. **回滚是可靠的**:两次都把文件系统和运行中的 Postgres 一起带回检查点。
5. **fork 和回滚的延迟随内存增长**:这里内存 1–1.4 GiB,每份 2–3 s、回滚 3–5 s。离"毫秒级"的宣传差得远,要查是复制内存还是恢复慢(缺口 6)。

**缺口 6(新)**:fork / 回滚延迟与驻留内存近似线性,是否可以用 uffd 懒加载或共享内存层压下来。

## 12. 实验 3:真实任务走出口审批与审计(2026-11-04,D78)

**任务**:对控制面跑 `govulncheck`(D73 当时因盒子出口受限只能手工)。**做法**:`ops/dogfood-egress.py`——项目**成员**(不是 deployer)在出口全关的沙箱里干活,被拒时按失败信息里的域名申请放行,deployer 批准;事先不知道要几个域名。跑完读审计和出站日志,校验哈希链。

**结果**
- 任务完成:`No vulnerabilities found`,代码受影响的漏洞 0 个,另有 1 个在依赖模块里但代码没调用。D73 的手工项现在可以在沙箱里做。
- 审批流:**2 轮**(`goproxy.cn` 装工具,`vuln.go.dev` 取漏洞库),每轮申请 202 + 批准 200;脚本里 0.05 s,真人审批的延迟没量。收紧(改回 closed)立即 200。
- 出站日志:13 条决定,放行 6、拒绝 7(被拒的就是第一次失败的请求)。
- 审计链:`/audit/verify` ok(6838 行)。这次运行的审计可以还原:`create → network_relax_requested → network_relax_approved → … `(成员申请、deployer 批准,各两次)。

**暴露的问题**
1. **被拒的错误不告诉 agent 该做什么**:只有 `Forbidden`,agent 得自己从错误里认出域名并去申请。该在 502/403 里带上"出口被拒:host=…,可 PUT /network 申请"的提示,或给 SDK 一个 `network.request(host)`。
2. **控制面的审计链看不到执行了什么**:链里没有 `exec`、文件读写,只有创建与网络申请。节点自己的审计日志其实记了 exec(命令前 200 字符、退出码),但它按节点分散、不在哈希链里;出站日志也在节点上,只留最近 200 条。"它做了什么"要到节点上去拼。
3. **批准人的标识是 `default`**:用 deployer 令牌批准时审计里的 `by` 是 `default`,分不出是谁点的批准。
4. **`network_relax_*` 审计行没有 `project` 字段**:按项目过滤审计时看不到它们(成员只能看到带项目的行,所以成员也看不到自己的申请)。
5. **OOM 杀进程只留下退出码 137**:2 GiB 的沙箱里 govulncheck 被内核杀掉(峰值约 1.9 GB),exec 结果里没有提示,要进沙箱 `dmesg` 才看得到。应当把 OOM 作为事件或 exec 结果的字段抛出来。
6. **开发模板内存不够这个任务**:换成 4 GiB 才跑完;`template_key` 又要求内存和模板一致,所以这类任务没法借模板的快照加大内存。

**没测的**:凭证注入(这个任务不需要凭证)。

## 14b. 缺口 6 查清了(D81)

对照测量(一个 2 GiB 沙箱;空闲 / 占 1 GiB 内存不写盘 / 写 1 GiB 文件)。"随内存增长"不准确:时间主要花在**恢复前把内存链合并成一个文件**(盒子上 uffd 关着,原因 `vm.unprivileged_userfaultfd=0`),其次是整份拷贝可写层。快照加载本身只有约 10 ms。

| 状态 | 回滚合并 | 回滚拷可写层 | 回滚总计 | fork 1 / 3 份(旧) |
|---|---|---|---|---|
| 空闲 | 1.2–1.6 s | 0.8 s | 2.2–2.6 s | 1.7 / 5.2 s |
| 占 1 GiB 内存 | 1.8–1.9 s | 0.8 s | 3.2–3.4 s | 2.5 / 6.7 s |
| 写 1 GiB 文件 | 4.2–4.4 s | 2.2–2.4 s | 6.8–7.2 s | 4.4 / 11.4 s |

写文件那一行合并也慢,因为被释放的页缓存脏页仍在内存差分里。修法(D81):每个检查点只合并一次并缓存,回滚和所有克隆共用。之后:fork 3 份 1.6 / 1.5 / 3.9 s,重复回滚 0.9 / 0.9 / 2.3 s。剩下的是可写层拷贝(ext4 无 reflink),随磁盘占用线性增长。

uffd 能从根上去掉合并,但需要改主机全局设置(`vm.unprivileged_userfaultfd`),jailer 下的 VMM 没有别的办法;三个选项与倾向记在 D81。
