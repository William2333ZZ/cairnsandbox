# 008 工作台

本文描述人怎样看和操作这套系统。它建立在 [001 用户使用过程](001-journey.md) 与 [003](003-sandbox.md) 到 [007](007-evaluation.md) 之上。工作台是我们自己的前端与后端(`decisions.md` D12),形态是 Codex / DSH Super-agent 一类的 agent 工作台:人把事交出去,agent 在 microVM 里做,人在面板上验收。参考材料与取舍在 `research/workbench-references.md`。

## 三个问题

打开工作台按顺序回答用户的问题(001 第 3–5 阶段),运维的问题在后面:

1. 我的 agent 在找我吗?(做完了要验收、卡住了要回答、要我做决定)
2. 我交代的事到哪了?(每件事的时间线,展开能看每一步)
3. 它健康吗,在做对的事吗?(沙箱、评测、版本、节点——次级页面)

一件工作的来龙去脉(Trigger → Eval → Ticket → PR)和一个版本的来龙去脉(候选 → 批次 → 晋升)是第 3 个问题的展开。

## 中心对象与主界面

工作台的中心对象是 **用户与他的 agent 的一段对话**(001);一件事(Ticket)是对话里的一段,CairnSandbox 版本在对话里只以"更新了"出现。主界面照 DSH / ZCode 的会话式工作面来做,以工单为段落——因为各渠道的 Thread 还没有并成一段对话(002"用户的词与概念"),合并之后左栏的列表变成一段对话里的事,中栏不变:

- **左栏**:工作区(仓库)→ 工单列表,像 DSH 的 Session 树:运行中(呼吸点)、等人(警告点)、有未读结果的标记;水位线;置顶与最近更新排序;底部"新工单"。
- **中栏**:一张工单的会话流。按派工分段,每段里是 agent 的每一步:模型的思考与说明、命令与其输出(折叠,失败标红)、Report 卡片(ready 带 PR 链接与 diff 摘要;waiting 带问题与回答框)、人的输入、回帖、策略变更。运行中流式跟随尾部(harness 每步写轨迹、ABI 每步一条事件),直到用户上滚。底部是输入框:追问或回答、停止、重试、换一个 CairnSandbox 版本重跑、打开右栏。
- **右栏**:停靠面板:文件、diff、终端、事件流、版本。
- 待处理、评测、版本树、节点、设置是次级入口(左栏底部),不再是首页;打开工作台默认落在左栏第一张等人的工单,没有就是最近更新的那张。

这与 DSH、ZCode 的差别只在中心对象:它们的中栏是聊天,我们的是工单的执行记录;它们的左栏是本机目录里的会话,我们的是仓库里的工单。

## 布局

三栏,照 DSH 的让步规则:

| 栏 | 内容 | 规则 |
| --- | --- | --- |
| 左栏(导航) | 上半是用户的:需要我(待批准、待回答、待审阅)、在做的事、例行、接入、记忆;下半是管理的:沙箱、评测、版本、节点、设置。事的列表带水位线:只显示前 5 条加正在运行、等人、有未读的那些,其余"展开其余" | 264 到 420 px,默认 280;低于 1024 px 自动收起成 56 px 控制栏;低于 768 px 变抽屉 |
| 中栏(对象) | 首页是 Conversation:一条流,用户的消息、agent 的话(ack / ready / stuck / question / approval / update / digest 各有卡片形态)、每件事的 work 标记;底部输入框,选中一件事时输入是对它的插话,否则是新的话。管理页是一个对象的详情:工单、沙箱、批次、Run、版本、Thread;或一个列表 | 至少 400 px;右栏先让步 |
| 右栏(面板) | "看着它干"的停靠面板:终端、文件、事件流、轨迹、diff、模型调用 | 首次打开占视口 45%,记住用户宽度,上限 70%;不够时先缩到 300 px 再提示占用方关闭;标签可分裂、可拖、操作可逆 |
| 底部槽 | 一条可选的全局条:正在执行的派工数与预算消耗 | 空时不占空间 |

## 分屏

照 ZCode 的分割树,只取两片叶子:`#/w/<a>?split=<b>` 把两件事并排,各自有标题行、时间线与输入框;左栏标题行的"并排…"选另一件事,右栏的"关闭"回到单栏。右栏打开时仍可用 `?rail=` 开停靠面板。

## 任务内循环的界面

对一个工单:参考执行的轨迹;两个候选编辑的 diff;fork 探测的对照结果,匿名呈现,不显示哪个 harness 产出;采纳、合并或拒绝;反思写入改进库的条目。评测分数、rubric、验收脚本在这里永远不出现。

## 共用的视图

- **事件流 / 轨迹**:按轮次分组的事件表加时间概览;只渲染可见行;流式时跟随尾部直到用户上滚;进行中的记录只显示开始标记,不虚构耗时。Run 与派工共用。
- **派工树**:页头的谱系面包屑加后代数;展开行才加载嵌套。fork 探测的候选沙箱在这里。
- **diff**:分支对基线的统一 diff,文件级折叠;PR 打开后链到 Gitea。
- **终端**:PTY 会话,运行中的沙箱才有。

## 后端

工作台只经控制面说话:`/sandboxes`、`/nodes`、`/eval/*`、`/intake/*`,鉴权是控制面的 bearer。为工作台要加的接口:

| 接口 | 用途 |
| --- | --- |
| `GET /events/stream`(SSE) | 控制面汇聚节点健康、沙箱状态变化、接单层的工单与 Decision 变化、评测批次进度;工作台不再轮询 |
| `GET /intake/tickets?source=&stage=&q=` | 列表的筛选与搜索 |
| `GET /eval/versions/tree` | 版本树:节点、边、状态、每节点的均值与后验 |
| `GET /eval/evolve` | `evolve.json` 的迭代记录 |
| `GET /sandboxes/<id>/diff?base=` | 沙箱内分支对基线的 diff(root 执行 `git diff`) |
| `GET /intake/conversation?since=`、`POST /intake/conversation {text, ticket?}` | Conversation 的流与输入框;带 ticket 是插话 |
| `GET /intake/approvals`、`POST /intake/approvals/<id> {decision, reason?, override?}` | 待批准与同意 / 否决(否决时可写一句为什么,它会记住;审查拦下的要二次确认才能同意) |
| `GET /intake/corrections`、`GET /intake/ask` | 纠正的清单;该问就问的读数(有用 / 不该问 / 该问没问 / 提醒次数) |
| `GET /intake/routines`、`POST /intake/routines/<id>/disable` | 例行 |
| `GET /intake/connectors` | 接入 |
| `GET /intake/memory`、`PUT /intake/memory/profile`、`DEL /intake/memory/<layer>/<id>` | 记忆 |
| `POST /login` | 换取控制面 bearer(部署者令牌或用户令牌) |

接单层与评测器各自保持自己的 API,控制面只转发与汇聚。

## 技术选型与构建

React 18、TypeScript、Vite、Zustand;Tailwind 只生成工具类,颜色与字号全部是 CSS 变量;不用组件库,基础组件自己写。构建在 Mac 上(服务器出不去),`web/dist/` 作为静态文件进仓库,控制面在 `/ui/` 直接提供(有 `dist/` 用它,否则回落到 `web/legacy/` 的旧页面),部署形态不变。`web/src/` 是源码,Vite 的开发代理指向本机转发的控制面。

## 插件化(D13)

照 DSH 的组织方式:内核(`src/kernel`)只是一个注册表加插件生命周期——导航项、路由、右栏面板、命令、slot、服务、事件;插件声明 `requires`,内核按依赖顺序激活,停用时撤回它注册的一切。外壳(`src/layout/Shell`)只渲染注册表里有的东西。每个功能是 `src/plugins/<名>` 下的一个插件:

| 插件 | 贡献 |
| --- | --- |
| rails | 右栏面板:终端(PTY 会话)、执行(流式 exec)、文件、事件流、diff(分支对基线);任何页面以 `?rail=<id>&sandbox=<id>` 打开 |
| attention | 待处理页与根路由,导航徽标 = 等人的工单数 |
| intake | 接单页、工单详情、Thread 详情、策略编辑 |
| sandboxes | 沙箱列表、新建、详情与操作;详情页有检查点(打 / 回滚 / 从这里 fork / 删)、端口地址、卷、环境、限额(D41/D42) |
| eval | 评测页(任务集、版本、新批次、批次列表)、批次矩阵、Run 详情 |
| versions | 版本树(父子、状态、最近批次均值与接受判定)与自动迭代记录;依赖 eval |
| nodes | 节点页 |
| settings | 外观、控制面令牌、已激活的插件 |

`src/api` 只有 HTTP 与 SSE;`src/store` 是 Zustand 状态,页面经它读写;`src/ui` 是无业务的基础组件与领域徽章。加一个页面 = 写一个插件并在 `plugins/index.ts` 加一行;改一个功能 = 改一个目录。

## 设计系统

`web/DESIGN.md` 是给改这个前端的 agent 读的规则文件,照 ZCode 的做法:

- 产品性格:安静、密集、可操作;长时间开着看;键盘可达;亮暗两套主题。
- 字号只用 `text-ui-xl / lg / base / caption / sm / xs` 六档;代码、diff、终端用自己的独立字号设置。
- 颜色只用语义 token:背景、面板、卡片、弹层、输入、边框、主次三级文字、品牌、成功、警告、破坏、"等人"。状态色只用于状态,不为了醒目借用。
- 阶段徽章、报告状态、Decision 结果各有固定的色与词,全站一致。
- 数字只在改变人要做的事时出现;健康状态不占地方;破坏性操作要确认;每个设置块一条保存栏。
- 这些是约束不是风格建议;违反算缺陷,CI 里有检查(字号类名白名单、颜色字面量禁用)。

工作台自己就是接单层的第一个"用户项目"(D8、D12):改它的工单走同一条路,PR 由人审。

## 搜索

按文本、id、Gitea 链接找 Trigger;按 `#12` 或 URL 找 Thread;按标题找工单;按版本 id、任务 id 找批次与 Run。

## 原则

1. 每个元素回答三个问题之一,否则删掉。数字只在改变人要做的事时出现。
2. 分类可检验、互斥、穷尽,如工单的阶段;标签说这一行等谁、要什么,不是内部状态码。
3. 一个概念一个位置:沙箱在沙箱页,Thread 与 Trigger 在接单页,批次在评测页;待处理只汇总并链接。
4. 面板用领域术语;内部标识折叠在详情里。
5. 计数等于它链接的列表长度;状态互不矛盾。
6. 健康状态不占地方;问题必须可操作,一次性网络错误不算;需要人的行直接给出操作;破坏性操作要确认。
7. 控件一致;每个设置块一条保存栏,只在有改动时出现。

## 客户端与本地站点

桌面端用同一前端;本地站点是桌面端拉起的一个节点代理,注册到同一账号,走同一协议,列表里以站点标记区分。本地只运行云端已晋升并签名的 CairnSandbox 版本,不做自我改进;用户选定一个工作文件夹以写时复制挂入,agent 的修改先落在叠加层,以差异呈现,确认后才应用到真实文件;默认断网;本地内容默认不上云,只同步元数据到审计。

## 云(沙箱侧的对象)

`#/home`「我的目录」(D29):个人 harness 目录的文件列表与编辑器(`/intake/home`、`/intake/home/file`),check 不过的问题顶在上面,机器的提案只列不搬。`#/cloud` 现在叫**控制台**(D47,参考 CubeSandbox 的 WebUI:概览 → 模板 → 沙箱,再往多租户走):顶栏有项目切换(写进 `X-Project`,所有建 / 配额 / 账单调用随之),六个标签——**概览**(节点存活与容量、本项目沙箱按状态 / 优先级、今天花费、等批的放宽、最近的事)、**项目与成员**(账户、项目、配额、默认网络、成员邀请 / 换令牌 / 有效期 / 移除,顶上是等你批的出口放宽)、**账单**、**卷**、**模板与构建**(多节点时多一张模板分发矩阵)、**审计**(按项目 / op 过滤;admin 可核对哈希链)。原来的四个标签是 [002 沙箱侧的领域](002-domain.md) 的直接视图(D33–D38):**账户与项目**(账户、项目、配额、成员,成员令牌只显示一次)、**账单**(今天与近 30 天按用量种类的行项与总额、价目表的版本)、**卷**(名字、项目、节点、大小、挂在谁上;建与删)、**模板与构建**(发起 OCI → 层或沙箱 → 模板的构建并看进度,各节点的模板与层)。节点页多了 cordon / uncordon / drain / evacuate 与"均衡一次"。成员看到的是自己账户的;部署者看到全部并能建账户、改价目表、手动计一次量。
