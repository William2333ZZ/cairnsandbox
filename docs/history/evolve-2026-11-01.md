## 学到的

1. **元 agent 两次盯上了同一个真缺陷**:启动器把 `PYTHONSAFEPATH=1` 放进了环境,它会传给 agent 跑的每个 shell,于是任务目录里 `python -c "import 同目录模块"` 失败,agent 在导入路径上空转。这是我们在启动器里埋的 bug(为了不让仓库里的 `aios` 包盖住 harness 层的那份,应该只用 `-P` 标志)。已改:标志保留,环境变量去掉,harness 的子 shell 也不再继承 PYTHONPATH。种子要重新建基线。
2. **critic 的两次误判都来自过宽的正则**:提到"tests"不该算引用验证材料;`grep` 不该算任务名。已改成只匹配验证路径、分数标记、完整任务 id 或八个字符以上的练习名。
3. **烟测用单次运行太狠**:种子在 beer-song 上三次全 1.0,候选一次 0.0 就被淘汰。按 007 的规则这是设计;但它让烟测成了噪声放大器。备选:烟测每题跑 2 次,全失败才淘汰。
4. **δ = 0.145 意味着只能检出大提升**:19 题 × 3 次,半分法把 3 次拆成 1 对 2,方差大。要把 δ 压到 0.08 以下,要么 k = 5,要么核心集 40 题以上。这就是 007 第 6.3 节写的事实,数字第一次有了。
5. **成本也要进门**:第 4 轮候选每次运行贵 50%(提示更长、更多回合),分数却没变好。接受门现在记成本并在只有"不劣化"时拒绝贵的。
6. **提案的方向单一**:四轮都在改提示和子 shell 环境;没有碰工具语义、观察格式、重试这些收益更稳的组件(文献的结论)。下一步给元 agent 的提示里按 8 个组件轮流指定方向,或者一轮出两个提案(Harness² 的 k = 2)。

## 第五轮(修了启动器之后)

新种子 `seed-polyglot-2` 基线均值 0.707(批次 b-c76c704279;和旧种子的 0.764 之差本身就说明两次独立评测差 0.06 是常态)。第五轮的方向是观察格式:候选把命令输出改成带退出码与失败标记的分节、长输出保留头 4k 尾 6k 并按行截断。结果均值 0.814,配对差 +0.107,bootstrap 95% CI [0.015, 0.233],每次运行 0.020 对 0.027 美元,更便宜。但按半分法算的 δ = 0.151 把它挡在噪声带内,入档未接受。

这暴露了 δ 的估法问题:k = 3 的半分是 1 对 2,方差比两次 3 次评测之差大得多。改成每题有放回各抽 k 次的两次模拟评测,δ 降到 0.08 一带,与"两个种子之差 0.06"一致。重算之后这个候选应当被接受——见下一节的 rejudge 结果。

裁决:第四轮候选仍不接受(配对差 −0.044,且每次运行贵 41%,成本门也拒);**第五轮候选 v-cb723f943c 接受**:配对差 +0.107 > δ 0.087,bootstrap 95% CI [0.015, 0.233] > 0,每次运行 0.020 对 0.027 美元。它改的是观察格式:命令输出改成带退出码和失败标记的分节、长输出保留头 4k 尾 6k 并按行截断。这是文献里说收益最稳的那类改动(观察格式),也是第一个由循环自己提出、自己评出、进入档案成为父代的 Cairn 版本。第六轮从它出发。

## 第六轮

Thompson 抽样把旧种子 `seed-polyglot`(修启动器之前的 harness 层)抽成了父代:它和新种子、被接受的候选一样"合格"。候选只改了 7 行观察格式、没写 CHANGES.md,结果均值 0.687 对 0.764,配对差 −0.078,CI [−0.167, −0.009],明确变差,入档不接受。花 1.65 美元,六轮共 10.31 美元。

改法:新种子登记时把旧种子标为 superseded,旧种子及其子树不再是父代;合格集合 = 当前种子 + 它的被接受后代。第七轮起父代只会在 `seed-polyglot-2` 和 `v-cb723f943c` 之间抽。

## WorkBuddy 迁移实验(第一次)

基线 b-27bbbf6be6:seed-polyglot-2 在 WorkBuddy 演化组 30 题 × k = 3,均值 0.807,δ = 0.034,花 4.64 美元;90 次里 6 次基础设施失败,全部来自两道工作区超过 48 MB 的题(`audio_scan`、`header_dimensions`,ws.tar 经文件通道传进客户机时被截断),这两道题要么从导入里剔除,要么等文件通道支持分块。

比较 b-c65f581b1a 没有得出结论:候选在 smoke 阶段就被淘汰,理由 `smoke: wb-refactor-medium-request_merge_path`。查运行记录,两次 smoke 都打了 0.75 分——WorkBuddy 的 script_verifier 给部分分,而 smoke 规则把"不满分"当成失败。这是评测器的规则错误,不是候选的问题:smoke 的目的是便宜地挡住跑不起来的候选,所以改成只有 0 分才算失败(`eval/evaluator.py`)。修复后的重跑排在第八轮之后(chain9),结果补在这里。
