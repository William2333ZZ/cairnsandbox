## 一、走一遍:每一条做的是否是承诺的

| 走的 | 做了什么 | 看到什么 |
| --- | --- | --- |

## 二、第一次在用户自己的任务上评测:先是全 0 分,然后发现是工作区错了

`eval/mine_history.py` 从仓库历史里挑出同时改了 Python 源码和 Python 测试的提交,导入成任务:提交前的工作区、提交带来的测试(隐藏)、源码改动(参考)。13 个提交、再造 8 个"缺一个决定"的 obstacle 变体。

第一次基线:**全是 0 分**。差一点写成"自己仓库的任务对 agent 太难"。查下去是两个洞:

1. **从沙箱读文件最多给 1 MiB**(节点只读一次,guest 的 `read_file` 不指定 `max_bytes` 就是 1 MiB):评测的工作区 tar 有几 MiB,到验证沙箱里就是半棵树。此前的评测用的都是几十 KB 的小题。修:读到读短为止(`read_whole`)。
2. **挖出来的任务工作区多套了一层**:`git archive --prefix=repo/` 的第一项是目录 `repo`,旧代码只在第一项带 `/` 时才剥,于是 `init/` 里是 `repo/pkg/…`,隐藏测试里 `import intake` 找不到包。连**真实挖出的那道**(PR #4 那道,Gitea 的 tarball)也是这样。修:取所有项共有的那一层。

## 三、agent 不问:obstacle 题

同样 7 个提交,把请求里的一个具体决定拿掉(比如"一个暂停的沙箱最多保留几层自己的 Diff?"→ 请求里不提层数),回答放在 blocker 里;提示里写了 `QUESTION:` 怎么提交。

| | 平均分 | Ask-F1 | 提问次数 |
| --- | --- | --- | --- |
| 同样的提交,原始请求(上表) | 0.65 | — | — |
| obstacle 变体 | **0.40** | **0.0** | **7 次运行里 0 次** |

agent 在 7 次运行里**一次都没问**;缺的那一个决定让平均分少了约 0.25。这是 D17 说的"外层管得住它不乱说,管不住它该问不问"在真实数据里的样子。宿主的第二双眼睛(`intent.py`,Ask-or-Assume 的做法)只在真实工单里工作,不在这个离线评测里,所以这组数字量的是 harness 自己。

## 五、中途发现的两件事

- **余额**:接着跑"朝着该问就问去进化"的一轮时,元 agent 起不来:上游回 `402 Insufficient Balance`——DeepSeek 账户的钱用完了(这一晚在 harness 评测与走脚本上花了约 15 美元)。agent 和评测都调不了模型,要用户充值。顺手把这种失败变成一句清楚的话:宿主认出 402 / "insufficient balance",对话里说"模型服务商说余额不足,充值之后回复「继续」",自动发起的事停一小时(D20)。
- **评审**:让一个不看我写代码过程的 agent 通读这一晚的代码,验证过的十二处都已修(D19)。最重的一处就是上面的"工作区多套一层"。

## 六、这些数字说明什么,不说明什么

- 说明:用户自己的仓库上的任务有区分力(0 到 1 都有),agent 在上面能做出多数部分分;obstacle 的差距真实存在;任一"全 0 / 全 1"的批次先查工作区与验收。
- 不说明:候选在更多题、更大的 k 上的表现(k=1,11 题,区间很宽);合成 obstacle 题的代表性(题是模型从提交里挑一个事实造的,有"答案在改动里、请求没泄露"两道检查,但不是用户真提过的问题);历史提交的提示是提交信息,不是用户的原话。
- 下一步该做的不是再造题,是让真实的纠正与真实的提问积累起来——依赖题与 obstacle 题要靠它们。

## 七、第二天早上用存下的运行记录离线查出来的(没有花模型的钱)

余额用完之后,基线的 11 条轨迹还在评测器的状态目录里。逐条数命令的种类:

| | 数 |
| --- | --- |
| 以"超限"收尾的运行 | 8 / 11(1 次格式错误,2 次正常提交) |
| 从没改过任何文件的运行(30 步里) | 2 |
| 第一次改文件在第 16 步以后 | 5 |
| 因为"提交"这句话白花的步数 | 1 到 6 步(挖出来的任务没有 git 历史,提示却说"提交") |

三条结论:

1. **钱记错了**(D22):`LimitsExceeded` 大多出现在二十多步,因为每步整段历史按未命中价算。按真实的缓存价,同样的 0.5 美元能走远得多;之前"9 次里 9 次停在 0.5 上限"是记账的结果,不是 agent 的习惯。
2. **读得太久、写得太晚**:这是下一个值得试的 harness 候选。已写成可关的选项 `progress_nudge_at`(默认 0 = 关):走到该步时若工作树里还没有文件变过,说一次"你已经走了 n 步还没改任何文件,先挑最可能的地方改一小处并跑检查;若卡在只有人能定的决定上,现在就说"。它同时给"该问就问"一条路。要靠 `evolve.py candidate` 走完整的接受门,不是直接开。
3. **挖出来的任务的提示不再说"提交"**:工作区是 `git archive` 出来的,没有 `.git`;现在的提示写"代码在工作目录里,没有 git 历史;按现状评分,不用提交"。老任务保留旧提示,不改它们的指纹。

等余额恢复,这一晚排好的实验顺序:① 用新计价重跑基线(同一版本,看分数与花费);② 带 `progress_nudge_at: 15` 的候选对比基线;③ 记忆开关对照;④ 朝"该问就问"进化一轮;⑤ 成批压缩候选(只在阈值时压一次,保缓存前缀)。

## 八、再往下看一层:分数里的白送分(同一天上午,存下的运行 + 空改动重算,没有花模型的钱)

§二 的"平均 0.651"和 §三 的"0.40"需要换一把尺子再读。重验时发现挖出来的任务按测试文件给部分分,而多数文件在没人动工作区时就已通过。把每个任务"什么都不做"的分数(`noop_subtasks`)记下来,再用 D23 的提升量重算存下的那批运行:

| | 空改动 | agent 原始分 | agent 提升量 |
| --- | --- | --- | --- |
| 历史任务 11 道 | 0.559 | 0.651 | **0.091** |
| obstacle 变体 7 道 | 0.495 | 0.400 | **0.000** |

- 11 道里 **7 道 agent 的分数和空改动完全相等**;有区分力的只有空改动得 0 的 4 道:真实的 PR 那道解出(1.0),另外三道一点没碰着。
- obstacle 变体里 `o-9691b106` 的 agent 把原本通过的测试改坏了:原始分 0.22,空改动是 0.89。这种退步在旧分数里只显示成"少几分",在提升量里被扣成 0。
- 所以§二 的结论"用户自己的仓库上的任务有区分力(0 到 1 都有)"要收回:有区分力的任务很少,其余的"0.9"是白送的;§三 的"缺一个决定让平均分少约 0.25"也不成立:那个差距是任务集的构成,不是 agent 的行为。**Ask-F1 是 0(7 次里问了 0 次)这一条不受影响**,它不看分数。
- 根因是任务本身:那些"long"任务是一整天的大提交(6 个以上源文件),提示只有提交信息,隐藏测试却检查具体的名字和行为。agent 读很多、写很少(§七),写出来的也对不上测试用到的名字。下一步见 D24:把测试要用的、工作区里还不存在的名字从测试里自动抽出来,写进提示——这是写任务该有的样子,不是给 agent 加分。
