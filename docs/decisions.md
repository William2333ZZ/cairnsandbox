## D1. 产品功能分组:四组改为三组

**结论**:产品图里"我的沙箱"与"与 agent 协作"合并为"工作台",最终分为三组。

| 分组 | 内容 |
|---|---|
| 工作台 | 沙箱列表、从模板创建、暂停恢复与 fork、对话与任务、终端与文件、轨迹回放 |
| 实验 | 任务集与基线、版本树、候选对比与晋升、成本与噪声 |
| 治理 | 权限审批、网络策略、审计与成本上限 |

**理由**:
- 用户操作沙箱时,对话、终端、文件、轨迹是同一个工作区里的几个面板,不是几个独立功能;拆成两组只是在导航上制造层级。
- 产品的核心对象是**实验**(一次带基线和候选版本的 RSI 运行),不是沙箱。沙箱是实验的载体。导航应围绕"工作台、实验、治理"。
- v1 界面保持最小:沙箱列表、终端加对话、版本表格(先不做可视化版本树)。

**可推翻条件**:如果后续出现不做 RSI 只做沙箱管理的用户群,"实验"应变成可选模块。

## D2. 桌面端本地模式

**结论**:本地站点 = 本地启动的一个**节点代理**(Docker 后端),注册到同一账号,走同一套协议。与云端的差异只在策略。

| 项 | 决定 |
|---|---|
| 运行形态 | 桌面端内置或拉起本地节点代理,agent 与 Cairn 运行在本地容器里 |
| 文件访问 | 用户选定一个工作文件夹,以只读或写时复制方式挂入容器;agent 的修改先落在叠加层,**以差异形式呈现,用户确认后才应用到真实文件** |
| 网络 | 默认断网,按任务白名单 |
| 凭证 | 不挂载用户的密钥与 home 目录,模型调用通过桌面端代理 |
| 敏感动作 | 删除文件夹外内容、联网安装、执行有外部副作用的命令:需要用户确认 |
| 日志 | 本地全量记录,联网时同步到审计日志 |
| **RSI** | **v1 本地不做自我改进**。本地只运行云端已晋升、已签名的 Cairn 版本 |

**理由**:
- 复用节点代理,协议、事件、UI 全部不变,本地与云端只是 `site` 不同。
- 自我修改的候选版本不应接触用户的真实文件。RSI 只在云端沙箱里做。
- "差异后应用"把风险从"agent 是否可信"转移为"用户是否看过改动",门槛低得多。

**未解决**:本地容器依赖 Docker 或同类运行时,普通用户的安装门槛较高。备选是 Apple 虚拟化框架,工作量更大,留待用户反馈再定。

## D3. 监督者重新定义为"晋升控制器 + 已知良好版本"

**结论**:此前图中的"监督者"容易被理解成一个运行中的 agent 或沙箱。它不是。拆成两个确定的部分,且都**不含 LLM**。

| 部分 | 是什么 | 职责 |
|---|---|---|
| 外部评测器 | 沙箱之外的确定性服务,自己创建并持有评测沙箱 | 持有任务集与隐藏测试,运行评测,给结果签名 |
| 晋升控制器 | 沙箱之外的小型策略服务,独立进程、独立凭证、独立数据库模式 | 验证评测器签名,检查门槛(Gate 1/2、留出集、噪声阈值、预算),执行晋升与回滚,可强制终止实验 |
| 已知良好版本 | 注册表里一个带内容哈希、不可变的制品(stage 0 及后续人工确认的稳定版) | 回滚目标;基线比较对象 |

**部署与运维**:
- 与用户沙箱网络隔离,沙箱不能访问它们。
- 由平台运维方持有凭证,**不是任何用户的 agent 能触及**。
- API 面尽量小:接收评测结果、查询状态、触发回滚;全部操作写入只追加的日志。
- v1 内部单租户,可与控制面同机部署,但使用独立进程与独立数据库账号。

**理由**:隐藏集需要对 agent 隐藏,不需要对用户隐藏;评测器与晋升控制器越简单、越确定,越容易审计。让一个 LLM 参与"决定晋升"会把被优化的东西放进评判链路。

## D4. 重要修正:Cairn 内核的强制边界必须靠权限隔离,不能靠"代码约定"

**发现的问题**:此前把"Cairn 内核(区域 A)"和"Cairn 可变服务(区域 B)"画在同一个沙箱里。如果两者在**同一进程或同一用户**下运行,可变服务的代码可以直接改写内存或文件,内核的"不可变"只是约定,没有强制力。

**结论**:

1. **安全关键的限制放在 agent 够不到的地方**:

| 限制 | 强制位置 |
|---|---|
| token 与成本上限 | 控制面的模型 API 代理,按沙箱令牌计量 |
| 网络 | 宿主机侧网络规则 |
| CPU、内存、磁盘、进程数 | 节点代理设置的 cgroup |
| 审计日志 | daemon 实时流出到沙箱外只追加存储 |
| 晋升与回滚 | 晋升控制器 |

2. **沙箱内的 Cairn 内核只是一个特权分离的薄层**:
   - 以独立用户运行,代码与配置所在目录对 agent 用户只读;
   - 可变服务以非特权用户运行,启用 `no_new_privs`,禁止 ptrace,不持有额外 capability;
   - 可变服务只能通过 unix socket 的系统调用 ABI 与内核交互;
   - 内核在这里提供**语义**(能力检查、检查点原语),**安全上限不依赖它**。

3. **推论**:即使可变服务被改坏或被恶意改写,它也不能越过沙箱的资源、网络、成本和审计上限。最坏结果是该候选得分差而被淘汰。

**局限**:加固 Docker 的隔离弱于 microVM,同一内核上的权限提升漏洞仍然存在。所以 R2(开放服务代码修改)必须在隔离升级为 microVM 之后,这条依赖保持不变。

## D5. 先做小实验,再决定要不要建平台

**问题**:整套计划是"平台加 Cairn 加 RSI",总工作量大,而 RSI 在**你的任务上**能否带来超过噪声的提升,目前没有任何证据。文献中的提升来自特定编码基准和较大预算,不保证迁移。

**小实验(约 1 到 2 周,在本机 Docker 上)**:
1. 整理 30 到 50 个自己的任务及自动验收脚本,拆成演化集、留出集。
2. 取开源的自改进编码 agent(DGM 或 SICA 的实现;能否在 macOS 上直接运行需要先确认),接到这批任务上。
3. 先测噪声:同一版本重复运行,得到方差。
4. 跑少量迭代(预算固定),记录:留出集提升是否超过噪声、每次迭代成本、失败与作弊现象。

**判定**:

| 结果 | 动作 |
|---|---|
| 留出集提升超过噪声,成本可接受 | 继续完整方案 |
| 有提升但主要在演化集 | 先解决评测与过拟合问题,不急着建平台 |
| 无提升或被噪声淹没 | 缩小范围:先做沙箱管理加评测流水线,RSI 作为后续实验 |

**理由**:小实验的成本远低于建平台,又能提前暴露最大的不确定性(评测噪声、任务集质量、迭代成本)。评测任务集本身就是后续所有工作的前置条件,早做不会浪费。

## D6. 规模目标与扩展接缝

**目标**:用户工作台加 RSI 实验,同时存在几百到几千个沙箱。不对标 DSec 的几十万并发。

**结论**:现在就做下列接缝,其余后置。

| 接缝 | 做法 |
|---|---|
| 无状态入口 | API 层无状态可多实例;沙箱 ID 带路由提示,位置以路由存储为准 |
| 运行态归属 | 运行中沙箱的状态以节点为准,数据库只记生命周期转换,控制面对账 |
| 沙箱分类 | 持久型与临时型,存储、同步、保留策略不同 |
| 事件与审计 | 批量流水线;序号与哈希链按沙箱或分片切分 |
| 镜像加载 | 统一接口,当前整层拉取,以后可换按需加载 |
| 调度 | 采样加节点本地准入;评测沙箱按项目并发上限节流 |

**后置**:按需镜像加载、内存超卖与回收、CPU 分级调度、轻量函数后端、云上突发扩容。

**理由**:一次实验约一千个评测沙箱就需要多节点;但 DSec 的密度、镜像分发与内存管理属于大量底层工程,对当前目标不是必需。上面的接缝改动成本低,而一旦缺失,规模上去后很难补。

**可推翻条件**:如果要承载训练用的 rollout(几万到几十万并发),需要重新定位,重点转向调度、镜像分发与密度。

## D7. 沙箱内系统按层生长,语言按层定(2026-10-30)

**结论**:guest 不再是"一个 Ubuntu 镜像",而是五层配方加内容寻址产物(`architecture.md` 第 3 节):内核层、系统层(Debian essential,无解释器)、agent-runtime(Rust 二进制:sandboxd + Cairn 内核 ABI + 晋升进来的稳定组件)、agent-harness(Python/TS,自带解释器在 `/aios/`,RSI 改的层)、env(任务工具链,随任务集版本)。Cairn 版本 = runtime 层哈希 + harness 层哈希;稳定的 harness 组件逐步重写为 Rust 晋升进 runtime("Python 用来演化,Rust 用来冻结")。harness 语言是 Cairn 版本的属性,不是平台的决定。(2026-10-30 晚修订:最初的七层把语言运行时错放在平台层和工具链层。)

**理由**:Landlock 作用域(6.12+)能把"可变层只能经 socket 与内核交互"从约定变成强制;unikernel 没有多用户与 fork,做不了 guest 内隔离;元 agent 写 Rust 的成功率低、编译进循环太贵,所以可变层保持 Python。

## D8. 评测任务来自用户自己的工作(2026-10-30)

**结论**:演化集、验证集、留出集从用户项目里挖(挖空有测试覆盖的功能、藏起测试做验收);工作台任务流做任务内循环;公开基准只做回归。第一个用户项目是这个平台本身。自建玩具任务停用。

**理由**:自建任务对当前模型全满分,噪声基线无信息且花钱;公开基准测的是模型不是产品。评测器存在的唯一意义是"这个用户的事做得更好了吗"。

## D9. 两个改进循环,运行时由评测数据选(2026-10-30)

**结论**:任务内循环(Harness² 的 Propose/Probe/Compose,fork 做探测,不打分)产出候选与改进库;版本循环(评测器,噪声带、配对统计、级联、档案库)裁决晋升。L3 运行时在我们的种子与 Prime Agent 之间由同一任务集上的配对比较决定;Prime Agent 的 `/refine` 只能产出候选,不能自采纳。

**理由**:开放世界任务没有真值,只能对照;版本晋升必须有真值,否则对照证据会把作弊固化(Prime Agent 的 Factorio 案例、AIDE² 的 public/private 否决率)。

## D10. 接单层:任务入口是事件驱动的工单,执行单位是沙箱,凭证不进沙箱(2026-11-01)

**结论**:在控制面之上加接单层(`archive/intake-layer-2026-11-01.md`(现行:`005-intake.md`、`006-execution.md`)):Source → Trigger → Gate+Assessment → Ticket+Mandate → 派工到一台沙箱 → harness 经 ABI `report` 自报 → 宿主中继回帖/推分支。默认 observe 模式。领域模型取自 DeepSeek Super-agent 原型,改四处:执行单位是沙箱、凭证留在宿主、状态走 ABI、工单进料两个改进循环。

**理由**:D8 要求任务来自用户自己的工作,但没有入口;Super-agent 原型把"谁授权了什么工作"建模得最清楚,而它缺的隔离、评测、自改进正是我们已有的。先只做记录的 observe 模式,是版本晋升同样的"先看再放开"。

## D11. 公开基准作为小规模验证坐标,不作优化目标(2026-11-01)

**结论**:接入 Aider Polyglot(DGM 用过的演化集)的 Python 轨道作为任务集 `polyglot-py`,用来验证评测器的统计与自动化版本循环在别人用过的题上给出合理数字;演化集仍以用户自己的工作为准(D8)。

**理由**:用户要求"找现有优秀论文用的开源数据集做小规模验证"。D8 否定的是把公开基准当优化目标;作为外部坐标它恰好能回答"我们的管线和 DGM、SICA 的数字是否同一量级"。Polyglot 的每题自带测试与参考解,直接对上任务集格式,Python 轨道不需要新的 env 层。

**补充(同日)**:polyglot-py 种子基线上一半以上任务出现部分分与 0 分,不在天花板,坐标成立。按用户建议再接 Harness² 所用的 WorkBuddy-Bench Code 子集(54 题可直接进现有 env 层)作为更接近真实工作的第二坐标;JobBench 与 Harvey LAB 是 LLM 判官打分,不接。

**可推翻条件**:两个外部坐标上种子都在天花板或地板,则换 SWE-bench Verified 子集(需要每题一个 env 层)。

## D12. 工作台自己做,后端自己的,前端参考 DSH 但不挂在 DSH 上(2026-11-01)

**结论**:产品形态是 Codex / DSH Super-agent 一类的 agent 工作台:人把事交出去,agent 在 microVM 里做,人在面板上验收。前端与后端都是我们自己的;DSH 的信息架构(待处理优先、Source / Trigger / Eval / 执行 / 设置的分页、健康状态不占地方)作为参考,不把 DSH 当客户端。

**理由**:用户的判断——这个平台的 agent 在沙箱里持续优化自己,工作台正是它第一个要优化的"用户项目"(D8);挂在 DSH 的插件接口上会让前端的演进受制于别人的接口。我们相对 Codex / DSH 的差异(microVM、fork 探测、会变的 Cairn 版本)要在界面上可见,这需要自己的前端。

**可推翻条件**:两周真实使用后,面板上人要做的动作被证明只有 DSH 已有的那几种,且自研前端的维护成本明显高于插件适配。

## D13. 工作台按插件化组织:内核只有注册表,每个功能是一个插件(2026-11-01)

**结论**:前端照 DSH 的组织方式但不照搬它的规模:一个很小的内核(`web/src/kernel`)只提供注册表——导航项、路由、右栏面板、命令、slot、服务、事件——和按依赖顺序激活、可停用的插件生命周期;外壳(`web/src/layout`)只渲染注册表里有的东西;每个功能(待处理、接单、沙箱、评测、节点、设置、右栏面板)是 `web/src/plugins/<名>` 下的一个插件,在 `plugins/index.ts` 的表里增删一行就是加减一个功能。不做 DSH 的宿主注入入口图与按包发布,先在一个 Vite 工程内。

**理由**:用户要求"用 DSH 类似的插件化方式来做,未来方便改造"。这个前端会由 agent 在沙箱里持续改(D12),插件边界把一次改动限制在一个目录里,critic 和审阅都更容易;以后要拆成按包加载、要做桌面端或第三方扩展,注册表接口不用变。

**可推翻条件**:插件数超过二十个、或出现跨插件的大量共享状态时,再考虑按包拆分与宿主注入。

## D14. 产品由用户使用过程定义;中心对象是对话,工单是实现(2026-11-01)

**结论**:新的 [001](001-journey.md) 用用户自己的词写一个人怎样用这个平台(拥有、接入、交代、走开、被找、纠正、例行、它自己来活、记忆、变强十个阶段,只在做完 / 卡住 / 要决定时打扰),放在领域模型之前;每个部件要能指到某个阶段里用户看到的东西,指不到的不做。用户视角的中心对象是他和自己 agent 的一段对话,Ticket、Assignment、Mandate 是对话背后的实现;工作台的首页是对话,管理页次级。原 001–011 顺延为 002–012。

**理由**:用户的判断——"做产品是解决用户的痛点和使用逻辑",此前的文档从沙箱、接单、评测往上搭,是架构视角;对照 Lee Robinson《How always-on agents work》(CS146S,2026-10-08)与 Grok Bot 的产品([调研](research/always-on-agents.md)),它们的叙述从用户的一天开始,我们缺的恰是用户侧的对象(用户、我的 agent、对话、例行、批准、记忆)和"只在该说话时说话"的纪律。

**可推翻条件**:若真实使用中用户主要在管理页上操作(看工单、看沙箱)而不是在对话里交代与验收,中心对象改回工单。

## D15. 平台按 001 重设计:Agent 服务持有对话、批准、例行、记忆;agent 只经终态报告说话(2026-11-01)

**结论**:在 002 里加入用户看到的八个概念(User、Agent、Conversation、Connector、Approval、Routine、Memory、Update)与 Router,接单层改为 Agent 服务并持有它们;agent 对用户说的话只能由 Report 的终态、Approval、Update 和接单确认产生,不可逆动作只能提草稿、同意后由 Relay 执行;记忆由宿主在派工开始与结束两个时刻读写,进沙箱时标为信息;每次晋升对用户是一条 Update,用户可钉回上一版;工作台首页是 Conversation。实现名(Ticket、Assignment、Report、Mandate)不改。建造顺序在 011。

**理由**:001 定义了产品;对照它,缺的不是沙箱或评测,而是用户侧的对象和"只在该说话时说话"的强制。把说话、批准、记忆放在宿主侧的 Agent 服务而不是 harness 里,是 000 的要求:harness 会被 agent 自己改,纪律写在它里面不是边界。保留实现名是因为它们已在代码、契约与测试里,改名只有成本。

**可推翻条件**:真实使用两周后,若用户主要在管理页上操作、很少在对话里交代与验收,则中心对象改回工单(D14 同);若 say 的纪律在宿主侧强制后 agent 仍频繁用 question 打扰(每件事超过 3 次),再考虑把问题也纳入批准式的节流。

## D16. 不分期;Agent 服务按职责拆模块;评测的主来源是用户的事(2026-11-02)

**结论**:产品不再分"第一期 / 第二期":001 的十个阶段都是产品,011 维护一份按用户感受排序的工作清单,一次一件事做到"做完"(代码、测试、CI、部署、真实走一遍、文档)。Agent 服务从一个 1500 行的文件拆成按职责分的模块包(入口文件重新导出旧名,脚本与测试不变)。评测任务集的主来源改为用户交过的事:合并且带测试的 PR 自动成为该仓库任务集里的题,迭代驱动优先在它上面跑,公开集只做回归。

**理由**:用户的判断——"一件事一件事做,不需要分期";分期让"以后再做"的东西永远排不上。模块化是为了下面每件事都能在一个文件里改完、critic 能看懂 diff。任务来源改回用户的事是 000 的原则(评测只回答产品问题)在代码上的兑现:到目前为止演化都在公开集上,更新里报的数字不是用户的任务。

**可推翻条件**:若从用户的事挖出的任务三个月内不足 20 道、或区分力都在天花板,则公开集继续作主坐标。

## D17. 学习信号来自用户的纠正;考题是这个用户的历史;自改进要有变更清单;该问就问进评测(2026-11-01)

**结论**:对照 2026 年的同类产品与学术结论([调研](research/landscape-2026-11.md)),产品的下一步不是再加部件,而是把已有的三件事(记忆、评测、进化)用同一个信号接起来——用户的纠正。纠正成为记忆里的规则,也成为该仓库任务集里一道带依赖的题;记忆只按"同一个用户的下一件事好了多少"衡量;用户任务集加依赖题、障碍题(该问时问了没)、长题(部分分),进化只在它上面比较,公开集只做回归;每个候选版本带变更清单与归因,回退能说出为什么;question / approval 的精度与召回进评测;渠道进来的内容在 ticket 里标不可信,不可逆动作由进化循环之外的独立检查审;agent 互传之前先在 002 定所有权与交接。不做:训模型、桌面 computer-use、追公开榜单、workflow 编辑器。

**理由**:云端编码 agent(Devin、Codex、Copilot、Jules)没有记忆、不自改进;个人 always-on agent(Grok Bot、OpenClaw)不改自己的运行系统;自改进工具(autoresearch)没有用户。我们三样都有,只能靠三者互相喂取胜。学术上:冻结权重加外部规则从用户纠正学到的提升是从结果学的一倍多(Learning on the Job);只有带依赖的任务流能分出记忆设计好坏(AgentCL);记忆该按改善后续行为评而非召回(MCCL);harness 自改进的瓶颈是可观测性,且对"会弄坏什么"基本盲(Agentic Harness Engineering),评估器必须在循环外只读(Weng);前沿模型自己决定问不问时成绩只剩一小部分、真实会话里 44% 的轮次是用户在纠正(HiL-Bench、SWE-chat);长任务必须按子任务给分(Long-Horizon-Terminal-Bench)。OpenClaw 的技能市场三成多含提示注入,说明接进用户渠道的 agent 以安全为分水岭。

**可推翻条件**:若三个月内用户的纠正不足 30 条、或由纠正生成的依赖题在候选版本之间没有区分力,则记忆与进化仍各走各的,纠正只进记忆。若障碍题的 Ask-F1 在所有候选上都接近天花板,则第 13 条撤下。

## D18. 从真实走一遍学到的修正:怎样结束要写出命令、沉默的停不能开着、CI 同时一张、自己交给自己是"你来做"(2026-11-02)

**结论**:D17 的六件事做完后,在开发机上用真实模型走了一遍(corr-walk、review-walk、ask-walk),暴露并修掉了五处:①harness 的提示只说"以 `QUESTION:` 开头提交",模型不知道怎么提交一段文字(系统提示叫它"不要和别的命令合并"),所以 QUESTION、APPROVE、HANDOFF 在真实里几乎从不出现;现在提示里给出确切的命令形状(`cat <<'EOF'` 加标记行加消息)并要求完成时写一句话,评测的 obstacle 题用同一段话(单元测试钉住两处措辞一致,并真跑这条命令确认环境认得);②harness 停在步数或时限上时上报 `waiting` 却没有 attention,宿主什么也不说、单子开着——一天里 CI 红了六次,六张 CI 单各烧五毛停在上限上,成了僵尸;现在宿主把它当 stuck 说出来,带"要继续吗";③CI Source 同一时间只开一张单,预算 0.3;④平台自己干的活(CI、定时、评测)的日志行不再进别的事的记忆,空的笔记不记;⑤交接的接收者被告知"你同事 fix 专门做"时会想把事交给自己,现在宿主把它当作"这事就是你的,做吧"而不是向用户报卡住。另外 Router 对每个新请求都看有没有"交给 <agent>",不只看以 @ 开头的。⑥(在用户自己的历史任务集上第一次跑评测时露出)从沙箱里读文件的接口只给前 1 MiB——guest 的 `read_file` 不指定 `max_bytes` 就是 1 MiB,节点只读了一次:任何超过 1 MiB 的文件(评测的工作区 tar、大补丁)悄悄被截断,评测器解不开或验的是半棵树;此前的评测用的都是几十 KB 的小题,没碰到。现在节点读到读短为止(`read_whole`)。这是一个只有"用真实大小的仓库做任务"才会碰到的洞,也是为什么评测要从用户自己的仓库里挖题。

**理由**:每一条都是只有真实走一遍才露的:单元测试里报告是假的,不会遇到"模型不知道怎么写出 QUESTION";僵尸单在没有真实红 CI 的时候不存在。D17 说评测要回答产品问题,这五条是同一个原则的另一面——先真实走,再信数字。

**可推翻条件**:若换了更强的模型后不需要在提示里写命令形状(它自己会提交消息),可以删掉那段;若 CI 单一次只开一张让真正的第二个故障被拖延,改为按失败的步骤名区分。

## D19. 独立审阅找出的十二处,以及"挖出来的题全是 0 分"其实是工作区多套了一层(2026-11-02)

**结论**:让一个不看我写代码过程的 agent 通读 D17/D18 的代码,验证过的有十二处,都已修,各有测试:①陌生人的话也被认成纠正、写成"用户纠正过"的永久规则——现在只有可信的话(本人、名单里的人、系统)才教;②写给运行中 harness 的收件箱消息没有围栏、还会像人说话一样打断模型调用,围栏本身也能被正文里的结束标记提前关掉——现在不可信的话围起来、不打断、结束标记被转义;③批准的决定不是原子的,点两次预算批准加了两次钱——现在先认领(`deciding`)再执行,动作失败不算批准,留在草稿状态可重试;④受保护路径只看补丁里的 `+++ b/`,删除、移出目录、只改权限、二进制都绕得过——现在看补丁里点到的每个路径(新旧两个名);⑤harness 起草的 send / budget / routine 只带 kind,中继要的目标、数额、日程没有,草稿永远批不成——现在宿主按渠道与草稿文本推出来,推不出的审查拦下;⑥合并按审查时的头提交钉住(Gitea `head_commit_id`),PR 动了批准草稿同一行重新审查;⑦(最重)挖出来的任务的工作区多套了一层目录——`git archive --prefix=repo/` 的第一项是目录 `repo`,旧代码只在第一项带 `/` 时才剥,于是 `init/` 里是 `repo/pkg/…`,隐藏测试找不到包,**历史任务全是 0 分是工作区错了,不是题难**;现在取"所有项共有的那一层"剥掉;⑧导入接口里调用方给的路径、任务集名、任务 id 可以逃出任务目录,现在都限制在里面,`taskset.json` 的读改写加了锁;⑨模型写的正则可能是 `(a+)+$`,在引擎锁里跑会卡住整个引擎——嵌套量词、回引用、环视一律不收,被检的新增行最多看 1000 字符;⑩宿主内部出错的工单沉默地开着不动(`infra` 标记把说话也压了)——现在说出来;已有开着的 PR 时 agent 回一句"好的"不再把工单结束掉(之后的合并就记不到了);⑪交接出去的单被重新打开会有两个所有者——现在不会;⑫挖出来的题的验收脚本相信 agent 的目录:它自带的 conftest.py 能把所有测试标成跳过、被跳过的测试从分母里掉出去——现在删掉工作区的 conftest 与测试配置、跳过算没过、判分在隔离模式下跑。小的:`stop` 只认单独的一句(原来"stop using print"也会停掉活)、审查提示不再把密钥的前几位写进会发到公开 issue 的批准文字里、删掉的 agent 的循环与例行会停。

**理由**:写代码的人读自己的代码会读过去。这一轮的价值最大的不是哪一条,而是⑦:前一晚还把"全 0 分"当作"自己仓库的任务对 agent 太难"写进了结论——一个没被怀疑的数字,是错在最底下的东西。以后任何"全 0"或"全 1"的批次,先查工作区与验收,再谈难度。

**可推翻条件**:⑥ 依赖代码托管支持按头提交合并(Gitea 与 GitHub 都支持);不支持的托管退回到审查时的头检查。交接给一个事后才拒绝这条触发的接收者(策略忽略它)时,工作原来会丢——现在交出者的单要等接收者的 Gate 接下才结束,没接下就留在原处并告诉用户(`handoff_accepted` / `handoff_refused` / 十分钟超时)。

## D20. 每日上限、效率一臂、人写的候选走同一条路、余额不足说成余额不足、压缩默认关(2026-11-02)

**结论**:①它自己发起的事(CI、例行、评测)每天合计花费有上限(策略 `daily_budget_usd`,默认 5 美元),到了就停着、说一次;人开口要的事不受限,确认里多一句话;输入框旁边一直显示"今天花了多少 / 上限"。②接受规则多一臂:配对分数差不为负、每次运行花费不超过父代的 75%、没有丢稳定通过,就算改进——"同样的分少花钱"原来过不了任何一道门。③平台开发者(人)写的 harness 改动走 `evolve.py candidate`,和元 agent 的提案同一条路,不留绕过评测的后门。④模型服务商以余额为由拒绝(402)时,宿主说成"余额不足,充值后回复继续",自动发起的事停一小时,不再混成一句"failed: …"。⑤`compact_history`(旧输出缩成头尾)写进了 harness 但默认关:它是第一个走人写候选路径的改动,结果是每次调用小了四成、步数多了、分数与花费都在噪声里(0.693 对 0.651,0.451 对 0.425),没有被接受,所以不进种子。⑥评测的 cheat 信号里"工作区超过 5 MiB"改为"比起点多长了 5 MiB":从真实仓库挖的任务起点就比 5 MiB 大。

**理由**:①是一天里六张僵尸 CI 单烧三美元的直接教训;001 第 1 阶段本来就写了"每天能花多少",只实现了每件事的预算。②③是同一件事:评测规则只奖励"更高的分",所以有人要改 harness 的时候,最省事的是绕过它。⑤是 D18 的原则:先真实走,再信数字——一个听起来该有用的改动(每次调用省四成输入)在同样的钱下没换来更好的结果。

**可推翻条件**:若每日上限被正当的大批量工作频繁顶到(一周里超过三次被用户手动抬高),改成按来源分别设限;若效率一臂接受了几个之后分数的长期趋势在降(以用户任务集上的均值看),把 75% 收紧或加上"分数下界不低于父代 − δ"。

## D21. 第二次独立评审又找出的十处(2026-11-02)

**结论**:同样的做法——让一个没看我写代码的 agent 读,并且让它亲手验证——第二轮又找出十处,各已修、各有测试:①D19 ⑫ 的修法把"agent 的 conftest"和"仓库自己的 conftest"一起删了,有共享 fixture 的仓库里正确的解也得 0 分;改成:挖题时把起点工作区里的 `conftest.py`、`pytest.ini`、`tox.ini`、`setup.cfg`、`pyproject.toml` 存一份(`verify/_trusted/`),判分时删掉 agent 树里所有这类文件、换上任务自己的;②判分依然可以被带偏——`pyproject.toml` 里加 `-p evil` 插件、从自己的代码里打印 `PASSED …` 行、放一个叫 `pytest/` 的目录——现在结果读的是写在树外的 junit 文件、不读可被伪造的输出文本,名字像 pytest 的目录与 `sitecustomize` 被清掉,测试文件名里有空格也行(清单改成一行一个);③模型写的正则 `(a|aa)+$` 与 `.*.*.*.*=` 躲过了静态检查——现在每条规则的检查在自己的子进程里跑、两秒为限,超时的检查被停用(规则留作建议)并说一句,不再有冻住引擎的路径;④批准卡片在动作失败后(HTTP 200、状态 pending)把按钮藏了、显示成一个"pending"——现在显示错误、按钮还在;⑤重启时停在 `deciding` 的批准永远没人认领——现在 `recover` 把它放回草稿并写明"重启打断了,重试前先看看是否已经发生";⑥每日上限:被预算挡掉的 CI 与例行已经被记成"见过 / 跑过",所以对话里那句"等明天"是假的——现在越限时轮询者根本不碰、也不记,放开之后仍红的 main 会被看到;运行中的派工的花费现在也计入(同时起几件事不会一起溜过上限);上限不是数字时不再崩;"HTTP 402"不再被当成余额不足(代理自己的单任务预算用尽也是 402);⑦批准里 harness 带的 `to`、`text` 现在只有在草稿里看得见时才算数(用户读到的就是做的),PR 动了之后模型审查会再问一次;⑧工单里 `inputs` 里的不可信的话原来没围栏,多行评论可以伪造"- [owner] …"——现在围起来;⑨挖历史时非 ASCII 的测试文件名被 git 加了引号而被漏掉(`core.quotepath=off`),导入一个读不开的归档会先删掉已有的任务目录(现在先验证),文件的可执行位丢了(现在保留);⑩清单里字段写成数字或字符串不再让迭代崩掉,`submit_candidate` 不再因父代不在节点表里而把真正的种子整支标成过时、也检查了空的核心集,效率一臂要求配对差的区间下界不低于 −0.15(只靠点估计会因为"少探索"而被噪声接受并棘轮)。

**理由**:两轮评审里找到的最重的两条(工作区多套一层、判分被 conftest 带偏或把正确的解判成 0)都在"评测自己"里——一个会改自己的系统,最不能出错的是它的尺子;我写的修法本身也带了新的洞(D19 ⑫ → ①),所以修法也要被读。

**可推翻条件**:若每条规则一个子进程的开销在规则多了之后可见(现在是几十条规则、每次完成一次),改成一个子进程里串行跑全部并整体计时;若 `_trusted` 的复制让某些仓库的判分不再一致(例如 pyproject 里有构建配置),改成只复制测试相关的段。


## D22. 钱要按真实账单算:缓存命中不是未命中(2026-11-03)

**结论**:模型代理原来把所有输入 token 都按未命中价记账(每百万 0.30 美元)。DeepSeek 命中前缀缓存的输入是 0.006 美元,差 50 倍;agent 每一步都把整段历史重发一遍,绝大部分输入是命中。现在代理读上游用量里的命中数(DeepSeek 的 `prompt_cache_hit_tokens`,OpenAI 一类的 `prompt_tokens_details.cached_tokens`),价格表的第三个数是命中价(缺省等于未命中价,旧配置不变),命中数记进用量、响应头 `X-Tokens-Cached`、harness 的 `model_call` 事件、评测的每次运行和 Agent 服务的每次分派。

**理由**:用户自己的任务基线 11 次里 8 次以"超限"收尾,平均二十多步停在每次 0.5 美元上,而步数上限是 60——那条线是被虚高的价格抵住的,不是 agent 自己做完或放弃。之前所有以花费为轴的结论都建立在这个数上:效率一臂(D20)、"压缩候选成本 +6%"(压缩改写前缀,会让命中变少,真实账单只会更差,这条结论要用新的计价重测)、每日预算、版本的"每次运行花费"。调研里两条证据指向同一处(Don't Break the Cache;CliffCompaction/TokenPilot 说压缩的时机比方法重要)。

**可推翻条件**:若上游不回命中数(换了不报告的服务商),命中数为 0,计价回到未命中价,这是偏贵的一侧,不会漏掉花费;若命中价不再是未命中价的一小部分,价格表的第三个数改掉即可,代码不动。**之前文档里的花费数字都是未计缓存的上界**(见 history 里各处的注),不重写,用新计价重跑基线后另记。


## D23. 分数要量"这次改动做了什么",不是"这棵树本来就对多少"(2026-11-03)

**结论**:挖出来的任务按测试文件给部分分(一个提交带来几个测试文件,每个文件一个分),但这些文件里的多数在没人动工作区时就已经是通过的。基线 11 次运行里 7 次的分数**正好等于**什么都不做的分数(0.73 到 0.93)。所以"平均 0.651"量的是任务集,不是 agent。现在:检查任务时把空改动下每个文件的分数记进 `checks.json` 的 `noop_subtasks`;打分时,**空改动下没有全过的文件才是目标**,每个目标按"它剩下的差距这次补上了多少"计分,原来通过现在坏了的文件每个抵掉一个目标的份额,总分取在 0 到 1 之间(`lift_score`)。没有分文件分数的任务不变;每次运行另存 `raw_score`,两个都看得到。通过(满分)的含义不变:所有目标过且没有变坏。

**理由**:候选与基线比较、接受门、Pareto 一臂、更新里的"在你的事上好了多少",全部建立在分数上。分数里有一大块白送分,噪声带就被它压扁(0.693 对 0.651 的"+0.041"在这里毫无意义);而真正有区分力的只有空改动得 0 的几道题(基线 11 道里 4 道:一道解出,三道没有)。这是 D19 ⑦(工作区多套一层)之后第二次发现"尺子"出了问题——两次都是看了存下的运行记录才发现,不是看汇总数字。

**可推翻条件**:若按文件的分数在别的仓库上让目标过少(一个任务只有一个失败文件,提升量退化成 0 或 1),这类任务本来就是通过/不通过题,无需调整;若发现"原来通过现在坏了"的惩罚让正确的大改动吃亏(重构改了很多测试文件的行为),把它改成只对明确回归的文件计、或降权。**D22、D23 之前的所有分数和花费都不能和之后的比较**:要用新计分对同一批运行重算(存下的运行里有每个文件的分数)或重跑。


## D24. 挖出来的任务要写清测试用到的名字,任务集的版本跟着内容走(2026-11-03)

**结论**:①挖任务时用 `ast` 读隐藏测试的导入和属性用法,列出工作区里还不存在的名字("`pkg/mod.py` needs: …"、"new file `intake/commands.py`: …"),附在提示后面。只给名字,不给代码;不用模型。obstacle 变体里,含有被拿掉的那个决定的字眼的行会被去掉。②任务集的版本原来只是任务 id 的哈希,同一个 id 换了提示或隐藏测试,版本不变,前后两批会被当成同一把尺子;现在版本也哈希提示、元数据和隐藏测试的内容。

**理由**:D23 之后看到的真相是,大提交类任务上 agent 的提升量是 0。原因之一在任务,不在 agent:提示是提交信息,隐藏测试检查具体的名字,名字取得不一样,正确的解也是 0 分——这是 SWE-bench 系列里"题目没写清楚"的老问题,他们的补法也是把题目补到能被测试唯一判定。这一步是写题目该有的样子(一份真实的 issue 或 PR 描述会提到),不是给 agent 作弊:列出的只是名字。②则是因为 D22、D23 和这一步都会改变同一批 id 的含义,必须让版本能看出来。

**可推翻条件**:若补了名字之后提升量仍是 0,说明任务的难度在别处(行为而不是名字),大提交类任务应从有区分力的任务里剔出,留作"长任务"观察用而不计入接受门;若名字列表过长(一个大提交 20 个新名字),等于把接口设计交了出去,应按总数设上限并把超限的任务标成不适合。


## D25. 第三轮评审:不同尺子量出来的批次不互相比较(2026-11-03)

**结论**:一个不看我写代码的 agent 读了今天的改动,最重的一条是:D22(缓存计价)和 D23(提升量计分)改变了"一分"和"一美元"的含义,但批次里没有记下用的是哪一版,`evolve.py` 会拿旧基线和新候选比——候选看起来更差(提升量把它拉向空改动的水平)或更便宜(缓存价)。现在:批次记 `scoring` 版本和任务集版本;`evolve.py` 的基线只在两者都对得上时复用,比较批次与基线批次对不上就"没有判决";每次运行的 `verify.lifted` 说明这一分有没有按提升量算。同一轮还修了:①检查结果过期时(任务被重新导入、测试文件换了一批)提升量不再把满分的解压成 0,重新导入时旧检查先删掉;②任务集版本也哈希工作区(文件名与大小);③失败的重试花掉的模型费用记到那一行上;④代理拒绝没有价格的模型(原来按 0 计,预算管不住),上游不报用量时按请求与回答的长度高估,不再免费;⑤进度提醒:起点标记缺失就不提醒,不把 `.pytest_cache` 之类算作改动;⑥接口提示:测试自己改写的辅助模块、提交新增的子模块、`try`/`with` 下的定义不算缺名字,障碍题的提示在名字可能带出答案或答案没法比对时整体不给。

**理由**:评测自己的尺子出过三次问题(D19⑦ 工作区多一层、D23 白送分、这条),每次都是读存下来的东西发现的,不是看汇总。让"哪把尺子"成为批次的一部分,是把这类事从"靠人记得"变成"机器拒绝"。

**可推翻条件**:若两个批次因为任务集多了几道新题就被拒绝比较而让进化跑不动,允许在公共子集上比较(`tasks` 已经支持),而不是放松这条检查。


## D26. harness 的可变层按 AHE 的七部分分,中间件做成钩子(2026-11-03)

**结论**:①可变层的组件名统一成 system_prompt、tool_description、tool_impl、middleware、skill、subagent、memory(加兜底 config),文档、进化提示词、改动清单用同一套;旧名(observation、loop、prompt、tools、helper)读作对应的新名。②中间件不再是循环里的 if 分支:`aios/middleware.py` 里每个行为一个类,在 `config.json` 的 `agent.middleware` 里按名字(或 `{"class": "包.模块:类"}`)开关,三个钩子 before_step、before_query、after_step;压缩历史和进度提醒各是一个类,默认都不开。写不出来的中间件让 harness 启动失败,而不是悄悄不生效。③`aios/memory.md` 是 harness 自己的长期笔记(空的种子),每个任务开头带上,候选可以改。④护栏和用户的记忆不在可变层:护栏在 agent 够不到的地方,用户的规则与画像归宿主。⑤不变量写进文档与元 agent 的提示:改写早先对话会让前缀缓存失效。

**理由**:读了 AHE(arXiv 2604.25850)和 Self-Harness(arXiv 2606.09498)的全文。AHE:七个文件级部分,一次逻辑改动一个 git 提交,改动清单预测修好和变差的任务并在下一轮核对、按文件回退;消融里单加记忆 +5.6、工具 +3.3、中间件 +2.2,只改系统提示 -2.3;改动清单对"会修好什么"的预测精度 33.7%,对"会弄坏什么"只有 11.8%(论文管它叫对回归的盲视);十轮 k=2,按在进化集上的 pass@1 选最优配置,用 SWE-bench-Verified 做迁移检查;没有报花费,没有谈缓存,没有人在环里。Self-Harness:接受条件是进化集和留出集上都不退步,但留出集同时用来接受和报告结果,没有消融,没有花费,64 题里切出的集很小。对我们:a)我们的接受门由外部评测器执行,分 evolve/validate/test 三份,比这两篇都严;b)"对回归的预测不可靠"证明了外部的稳定通过保护(lost_stable)不能省;c)两篇都把只改提示当作最弱的一类,所以"提问措辞"候选的先验不高;d)没有人报告花费与缓存,我们的缓存计价和效率一臂在这方面是多出来的;e)AHE 把长期记忆放在可变层里并且收益最大,我们之前只有宿主管的用户记忆,现在补上 harness 自己的笔记。

**可推翻条件**:若 `memory.md` 里的笔记被进化写成针对具体任务的答案(critic 拦不住),给它加长度和任务名的检查;若中间件钩子的数量让改动互相干扰(AHE 观察到的"非加性"),按钩子逐个评测再合并,不一次加多个。


## D27. 对着 dsh-superagent 的文档逐条核对之后补上的(2026-11-03)

**结论**:读了它的 000 哲学、001 领域、002 授权、003 执行、004 提示、005 面板,和我们的实现逐项对照。核心模型(Source/Trigger/Thread/Eval/Mandate/Ticket/Assignment、门加判断两层、observe/auto、说话规矩、并发与保留位、外发的重试与退避、重启恢复)原来就有。缺的,现在补了:①**PR 属于开它的工单**:开 PR 时宿主把那个 PR 的 Thread 以 `own` 订阅给工单,之后人在 PR 上的评论接着这件事做,不再当作新的请求(003 §11、§47;原来没有,是对照时发现的真问题);②**订阅有两种**:`own` 与只读的 `context`,`context` 的消息送进去标为上下文,不唤醒已结束的工单、不算被接走(001);③**Correlation**:共享同一个 Trigger 的 Thread 互相关联,只给 Eval 加上下文,从不路由(001);④工单**卡住(blocked/failed)时不再自动推机器人和 CI 的消息**,记下但不送(003 §53);⑤工单自动结束时,**没读进去的人的话退回 Eval**(003 §39);⑥一个会话的**外发消息按排队顺序**,前一条失败或在等退避,后面的等着(003 §43);⑦**团队提示段落**(004):沟通、范围、交付三段,每次保存一个不可变版本,保存带基础版本、冲突拒绝、有上限、与内置相同等于没有覆盖、内置文字变了会标出;只是建议,宿主的检查不读它。

**没有照搬的**:003 里的后台任务与子 agent 规则(第 21 到 26 条)是针对它那种持续会话的执行器的;我们的 harness 是一个 bash 工具的循环,一个任务一个沙箱,没有对应物。它的执行会话以操作者用户无审批运行、自己写明不是安全边界;我们每个任务一个独立沙箱加预算和独立审查,更严。005 的面板里"评估重来"、搜索、设置的保存历史我们只部分有。

**理由**:你把 dsh-superagent 当作参照,我之前只核对了机制是否存在就说"基本满足",这次是逐篇读完再对代码。

**可推翻条件**:若 `own` 订阅 PR 让无关的 PR 评论(别人对同一 PR 的闲聊)不断唤醒工单,给 `own` 加上"只响应点名或列表里的人"的条件,而不是退回不订阅。


## D28. 看了同一个人的另一个产品之后:账户分开,证据规则对齐(2026-11-03)

**背景**:读了 all-products 仓库(固件开发智能体加主动录音卡,E2B 沙箱里跑 DSH)的设计决定 D1 到 D22,以及一份"AI 辅助研发与工程智能化平台"的总体架构文档。两者和我们做的是同一类事的不同层:它们是"包在编程智能体外面的领域 harness",我们是"让这层 harness 自己变好的系统"。

**结论**:①**模型账户分开**(它们的 D16):模型代理的令牌带一个账户名,`live` 是人在等的 agent,`eval` 是评测与进化;每个账户可以有自己的上游密钥(`UPSTREAM_KEY_FILES`,没配或读不到就用共享的,行为不变)。2026-11-02 夜里评测把余额花光,live 的 agent 也一起停了,正是它们记录过的同一件事。要真正隔开,需要给 `eval` 一把自己的 key(用户创建,我不创建账户),放在 `secrets/deepseek-eval.key`,启动模型代理时带 `UPSTREAM_KEY_FILES='{"eval":"/secrets/deepseek-eval.key"}'`;代理的 `/health` 会写明哪个账户用自己的 key、哪个在共享。②**证据规则对齐**(它们的 D21):任何新的验收断言先在故意弄坏的条件下跑一次,证明它会失败(我们的"空改动必须失败"检查就是这条,D23 又补了它没覆盖到的部分分);改 agent 指引或经验库之前先做 A/B,同一条提示、同一个构建、每组至少三次、报中位数和范围(它们量到经验库第一版让 flash 变慢:649 秒对 1119 秒,agent 还自己写了个 TrueType 解析器——规则加得多不等于效果好);文档不写没验证过的话(它们的规则是硬件没到之前不说"真机验证",我们是没跑过就不说"已验证")。③**指标的先后**(它们的 D2):复用质量 > 验收可信 > 人审负担 > 成本 > 速度,理由是数据显示瓶颈是人审和假通过,不是速度(每轮人审 1000 到 4300 行改动,前三轮各审出 4 到 7 个问题,到第三轮出过 5 次假通过)。我们的接受门现在只看分数与花费;**人审负担**(合并草稿的改动行数、审查提醒数、人驳回率)还没进指标,列为下一步。④**智能体可以换**(它们的 D22):harness 不绑定一个智能体主循环,默认 DSH,也接 Claude Code、Codex 等。我们的 harness 是自己的循环;要接进那份平台文档里的 Octop,应该做成它下面的一个专家(ACP、MCP 或 HTTP),这是后话。

**没有照搬的**:它们用 E2B 云沙箱,我们用自己的微虚拟机;它们的物理交互层(设备声明能力、主动策略、录音链路)是硬件产品的事,和我们无关;平台文档里的数据分级、内部模型路由、红队评测、Skill 生命周期是组织层面的要求,我们没做,见 landscape 笔记第九节。

**可推翻条件**:若分账户后 `eval` 的余额管理成了负担(两个账户都要看余额),退回单账户,但在代理里给 `eval` 一个日预算上限,让它花不到把 `live` 拖垮的钱。

## D30. 我们是云产品,沙箱层是必争之地:先对齐整车,再谈大脑(2026-11-03)

**背景**:对照 CubeSandbox 时,我把我们写成"一个人的平台、单机原型",把多副本控制面、节点调度、E2B 兼容、卷归为"它是云产品、我们不用补"。用户当天纠正:我们也是云产品,沙箱是必争之地,这些都要补。随后读了《腾讯云 Agent Runtime 往下挖,是一场 microVM 地基战》:三家云的 VMM 都在 rust-vmm 谱系里收敛,差距在"整车"——调度、快照恢复、资源池化、网络、存储、多租户、计费、规模化安全加固;Firecracker 只是发动机。

**结论**:①**定位**:Cairn 平台 = 一个沙箱云(执行面)+ 一个会自己改的 agent 面(大脑)。执行面要做到和 CubeSandbox / E2B 同一水平,这是入场券;大脑是差异。两层并存:用 E2B 接口进来的外部 agent 得到和别人一样的执行面;用我们 harness 进来的多得到预算、工单、inbox、评测与进化。②**沙箱层的对标清单就是那九样**(research/cubesandbox-vs-ours.md 的表),每项要有现状、缺口、数字;"没有同机 benchmark 就没有必争的资格"。③**要补的顺序**:多副本控制面(共享状态;节点仍是运行态权威)→ 节点调度补齐(TAP 池、资源打分、优先级类、带迁移的排空)→ E2B 兼容层(控制面前的翻译层 + 沙箱内 envd 形状的数据面)→ 原地 rollback → 卷 → audited 出口 → 模板带内存 → 同机性能对比。④**保留的选择**:"VM 就是环境 + 配方层"不改成 VM 里跑容器,但模板来源要能是 OCI 镜像;sandboxd 的 ABI 不被 E2B 层替代,是多给的一层。

**撤回的判断**:D-系列以前凡是写"单机原型阶段不需要"的地方(003 尚未实现一节的口气、本次对照的第一版),按本条改读。

**可推翻条件**:若一年内外部 agent(DSH、Codex、OpenClaw 等)接入我们的沙箱的实际需求为零,E2B 层可以降级为"有就行";但控制面、调度、卷、计费这四样不受此影响,它们是云产品本身的要求。

## D34. 检查点与原地回滚:沙箱 id 不变,层被钉住(2026-11-03)

**背景**:D30 清单第四项;CubeSandbox 对照里"我们缺原地 rollback";ABI 的 `checkpoint` 一直只记一条事件。agent 试错一轮失败后,工作台的长会话需要回到上一个点继续,而不是 fork 出一台新沙箱让 ticket 和 inbox 换 id。

**结论**:①检查点 = 运行中打的 Firecracker Diff 快照(设备状态 + 一层内存,加入链)+ 可写层 `upper.ext4` 的稀疏拷贝,放在沙箱目录 `ckpt/<name>/`;打完 VM 继续跑,guest 只停顿快照那段。②回滚原地做:杀 VMM 进程、把检查点的可写层 `cp --sparse` 回同一个 inode(jail 里的绑定视图跟着变)、从检查点的链 restore;id、目录、tap、IP、ticket.json、inbox 都不变;之后的暂停与检查点在它之上继续。③**检查点钉住它引用的内存层**:`_gc_mem` 的保留集 = 当前链 ∪ 所有检查点的链,链压缩与回滚都不会删掉另一个检查点要的层;删检查点时再 gc。④先在 Python 节点代理里做,是 Rust 重写的规格;节点 e2e `node/test-ckpt.py` 进 CI。

**真机上踩到的两个坑**:杀掉 VMM 后立刻恢复,内核还没释放 tap(Resource busy),恢复要重试;VM 的健康看门线程在 kill 时可能还卡在一次 ping 里,等它出来时新的看门已经启动,它那条迟到的"通道断了"会把刚恢复的 VM 当故障销毁——看门加了代号,只有最新的那个能宣告故障。两者在暂停 / 恢复里没暴露,因为中间有空档。

**没做的(写于当日;同日晚些的 D41 补上了前两项:检查点进 bundle,fork 可从检查点出发)**:检查点不进 bundle(export / 迁移 / 接管后检查点丢失);不能从检查点 fork(fork 仍从当前状态);存储用量没算进计量;控制面没有"检查点属于谁"的目录(002 的 state package 还只有 bundle),只经 exec 转发;ABI 里 harness 自己打检查点仍只记事件,宿主接上去是下一步。

**可推翻条件**:若可写层拷贝在大工作区上太慢(现在 512 MiB 稀疏文件几十毫秒到一两秒),改成可写层也走 Diff(qcow2 / 反射链接)。

## D35. 卷:独立生命周期的 ext4 镜像,附在沙箱上(2026-11-03)

**背景**:D30 清单第五项;D29 的个人 harness 目录每次派工 tar 一遍;CubeSandbox 的 Volume 框架是 E2B 兼容的形状。Firecracker 不支持热插块设备,卷只能在创建沙箱时附上。

**结论**:①卷 = 节点上的一个稀疏 ext4 镜像(`state/volumes/<id>.ext4`),有自己的 id、名字、归属项目、大小;控制面记它住在哪个节点(SQL `volumes` 表),成员只见本账户的。②创建沙箱时 `volumes:[{id, mount, ro}]`:控制面把沙箱钉到卷所在节点,节点把镜像硬链接进 VM 目录(jail 里同一 inode)作为 layers 之后的 virtio-block 设备,启动后在 guest 里按 /dev/vdX 顺序挂到 mount;带卷的沙箱冷启动(模板快照里没有这些设备)。③**一个写者或多个读者,不混**:节点在附卷时检查,违反回 429;销毁即解挂;重启后从回来的沙箱重建挂载簿记。④读者的只读在设备层(`is_read_only`)和挂载层(`-o ro`)都生效。

**补(同日)**:卷可以直接从一个 tar 生成(`/volumes/from-archive`,mkfs -d 不挂载);Agent 服务在 `INTAKE_HOME_VOLUME=1` 时把 harness 目录做成每摘要一个的只读卷附在 /work/home,旧版本没人挂着就删——D29 的下一步闭合了,但默认仍是 tar,因为带卷的沙箱冷启动,工单派工多走 0.4 秒。

**没做的**:卷不进 bundle(迁移、接管后要重新附,跨节点共享等对象存储后端);存储配额(max_storage_gib)仍只记录;E2B 形状的 /volumes 接口(带 auth token 的形态)未对齐;卷与模板快照不能同用(volumes 的沙箱不能热启动)。

**可推翻条件**:若"一次一个写者"在实际使用里太紧(多台沙箱要同时写一个工作区),换成网络文件系统(virtiofs 需要换 VMM,或 NFS 经出口代理),卷退化为只读共享。

## D36. 出口:L7 规则、audited 模式、凭证只在节点(2026-11-03)

**背景**:D30 清单第六项;003 里 audited 模式写了很久没做;CubeSandbox 对照里 CubeEgress 的规则 / 凭证注入 / 审计是参考。我们不做 HTTPS 中间人(D30 已定),所以能做的边界要说清。

**结论**:①每台沙箱的 NetworkPolicy = mode(closed / allowlist / audited)+ allow_hosts + allow_direct + rules。规则按序第一条命中为准,按 scheme / host(精确、`*.后缀`、glob)/ method / path(精确或前缀)放行或拒绝;没有规则命中时 audited 放行、其余按 allow_hosts。②**凭证注入只对明文 HTTP**:放行的规则可以要求代理加上节点保险库里一个凭证的头;CONNECT 隧道只看得到 host 与端口,method / path 规则和注入对它不生效。对外部 HTTPS API 的密钥注入经专用代理(模型代理就是),不做中间人。③**凭证只在节点**:保险库在节点进程内与一个 0600 文件里,控制面只负责把值推到每个活节点,自己不存,审计只记名字;沙箱里任何地方(环境、文件)都没有值。④每台沙箱最近 200 条出站决定(方法、主机、路径、命中的规则、注了什么)留在节点,控制面经转发读;审计日志每条照记。⑤校验两道:控制面 network 包在创建与更新时按同一形状校验,节点再校验一次。

**没做的**:带宽与请求数配额;按项目的默认策略(现在每台沙箱自己带);规则里的 host 通配只到后缀,没有正则;出站字节没进计量;规则变更没有审批流(003 写的"放宽要审批"仍在 Agent 服务那层由人同意,不在这里)。

**可推翻条件**:若实际需要对外部 HTTPS API 注入凭证的场景多于两三个,再考虑在出口代理上做带根证书的中间人(CubeEgress 的做法),代价是模板里要烧根证书、代理要签发叶证书。

## D37. 镜像:OCI 镜像成层,运行中的沙箱提交成带内存的模板,Build 是对象(2026-11-03)

**背景**:D30 清单第七项与对照里"模板来源要能是 OCI 镜像"、"模板带内存";002 的上下文 4 定了 Layer / Template / Build 三个对象。

**结论**:①**OCI 镜像成层**:节点从仓库(`REGISTRY_MIRROR`,默认 docker hub,匿名令牌)拉 linux/amd64 的清单与各层 blob,按序应用 whiteout,根文件系统用 `mkfs.ext4 -d` 直接写成一个只读层(不挂载、不起沙箱),登记进 LAYERS。它叠在我们的基础镜像之上,不是替换:guest 里的 init 与 sandboxd 仍来自基础,镜像的文件按 overlay 语义盖在上面。②**提交为模板**:运行中的沙箱 `commit {name}`:快照(内存链合成一个可直接映射的文件)+ 可写层拷贝,成为名为 name 的模板快照;新沙箱 `template_key=name` 从它热启动,内存里的进程也在;配置(模板、vcpu、内存、层)须一致,否则 400。16 位十六进制的 template_key 仍是放置提示,节点没有就按规格自己的键来。③**Build 是对象**:控制面 `POST /builds {kind: oci|commit}` 记一条(项目、种类、输入、节点、状态),异步让节点做,结果与错误写回;模板与层的目录从各节点汇总,带节点名。④检查点与提交共用一个"快照后继续跑"的原语(`VM.snapshot_live`)。

**补(同日)**:开发机连不上任何镜像仓库(docker hub 不通,阿里云加速器已停匿名 API),只有 docker 守护进程经它的加速器能拉。所以加了第二条路:`docker save` 或 OCI layout 的 tar 作为 body 上传(节点 `/layers/from-archive`,控制面 `/builds/archive`),同一套 whiteout 与 mkfs -d;CI 用这条路验证。仓库直拉的路保留给能连仓库的环境。

**没做的**:模板与层仍是节点本地的(分发经 `/templates/everywhere` 的导出 / 导入,层还没有跨节点分发的接口);OCI 镜像的 ENTRYPOINT / ENV 不解释(我们的沙箱不是容器,进程由 harness 起);私有仓库的凭证没接;Build 没有日志流;多架构只取 amd64。

**补(同日,真机上撞到的)**:busybox 镜像自带 /bin/bash(指向 busybox)和没有 agent 用户的 /etc/passwd,叠在基础之上后 guest 的 init 脚本跑在 busybox 的 sh 里,沙箱起不来。先试了一个"基础拥有的路径"清单,不够;现在的规则是**基础赢**:构建层时用基础镜像的实际文件列表(起一台一次性沙箱 `find / -xdev`,按基础镜像签名缓存在 state/ 下)把镜像里与基础重名的文件全部剔掉,镜像只补基础没有的。语义上等于把镜像层放在基础之下,但不用改 guest 的 init。

**可推翻条件**:若"基础赢"让某些镜像的核心文件(比如镜像自带的更新版 libc)被剔掉而跑不起来,再改成"镜像即根 + 我们的 sandboxd 作为一层注入",那就要给每个镜像配 init。

## D38. 节点与容量:cordon / drain / balance、优先级类、打分放置;TAP 池不做(2026-11-03)

**背景**:D30 清单第二项,CubeSandbox 对照里"资源打分、优先级类、在线均衡、带迁移的排空、TAP 池"。

**结论**:①cordon 是注册表里的一个标志,各副本一致,放置时跳过;显式钉住的创建不受影响。②drain = cordon + 用已有的迁移把该节点上每台 persistent 沙箱搬走,ephemeral 的留着到期;一个副本持租约做。③balance:最忙与最闲节点的负载(已用 VM 位的比例)差超过阈值就搬 persistent 沙箱,一次最多 max 台。④优先级类:interactive / batch / background;后两者只放到仍留有余量(2 个空位、1 GiB)的节点,默认 qos=be——评测与进化是我们自己最大的批处理来源,这条保证一波评测不把工作台的人挤掉。⑤放置从"抽两个取跑得少的"改成"抽两个取分高的":暖池 / 模板快照各加分,再看空位与空内存的比例。⑥**TAP 池不做**:我们的 VMM 在 jailer 下按沙箱分 uid,tap 必须以那个 uid 创建才能被无特权的 VMM 打开,预建的 tap 换不了主;而且我们建 tap 的成本是几十毫秒,不是 CubeSandbox 省下的那 59 ms 的量级。

**没做的**:优先级没有抢占(高优先级来了不会驱逐低优先级);balance 不看内存只看 VM 位;drain 不等迁移失败的沙箱自己退出;余量两个数是常量,没有按节点配。

**可推翻条件**:若评测并发到了一个节点被 batch 占满而 interactive 等位的程度,再加抢占(暂停最老的 background 沙箱)。

## D39. 端口暴露:沙箱里的服务经节点反向代理可达(2026-11-03)

**背景**:002 的上下文 8 列了 PortExposure;我们的沙箱没有入站,agent 起的 web 应用、E2B 形状的数据面(envd)都需要一条从外面到 guest 端口的路。

**结论**:节点是唯一能连 guest 地址(tap 另一端的 10.200.x.y)的进程,所以路在节点上:`/sandboxes/<id>/ports/<port>/<路径>` 反向代理到 guest 的 ip:port,控制面照常转发,鉴权与别的路径一样。明文 HTTP、整个响应、不做 websocket;暂停的沙箱透明恢复。不做 CubeProxy 那种 `<port>-<id>.<domain>` 的泛域名路由:那要 DNS 与 TLS,放到有域名的部署再说。

**没做的**:websocket 与流式响应;非 HTTP 端口(TCP 隧道);泛域名;按端口的访问策略(谁能看谁的端口只靠沙箱归属)。

**可推翻条件**:要接 E2B 的 SDK(它找 `49983-<id>.<domain>`),就得补泛域名路由与 websocket,到那时改成在控制面做一个真正的 ingress。

## D40. E2B 形状的控制面在第二个端口;envd 数据面不做(2026-11-03)

**背景**:D30 清单第三项"E2B 兼容层";地基战文章里国内两家都兼容 E2B 以承接生态;CubeSandbox 的 CubeAPI 证明这层是翻译。E2B SDK 的两半:控制面(REST:创建、列表、暂停、超时、删除、模板)和数据面(沙箱内的 envd,Connect-RPC,SDK 经 `49983-<id>.<domain>` 直连)。

**结论**:①控制面那一半做了:同一个 fc-cp 进程在第二个端口(8710)说 E2B 的话,`X-API-Key` 就是我们的成员令牌,templateID 映射到有名字的模板(D37 的 commit 产物)并热启动,timeout 映射到空闲 TTL(节点新加 `/ttl`),metadata 记在路由上,节点不见。②路径与 §1 不冲突所以不做前缀、不按 body 猜形状。③**envd 不做**:它要求泛域名入口、websocket 和 Connect 协议,而且把命令 / 文件的数据面放进沙箱里的一个守护进程——我们的数据面是 sandboxd 的 vsock 协议经节点与控制面转发,再加 D39 的端口暴露;E2B SDK 的 `commands.run` 这一半接不上。④所以今天"E2B 兼容"的准确说法是:E2B 的控制面 SDK 调用能用,数据面要用我们的接口。

**没做的**:envd 协议;泛域名与 TLS;E2B 的模板构建接口与 volumes 形状。(envVars 同日补上:节点把 spec.env 垫在每次 exec 的环境下,D41。)

**可推翻条件**:若外部 agent(DSH、OpenClaw)接入时确实只会讲 envd 协议而不愿改适配,再做一个 envd 兼容的守护进程(或在 sandboxd 上加一层 Connect 的皮)和泛域名入口;到那时 D39 的端口暴露就是它的底座。

## D41. 补差距一轮:保留期、从检查点 fork、websocket 端口、出口限额与正则、项目默认策略、结算账本、层分发、节点余量(2026-11-03)

**背景**:八个上下文落地后(D33–D40),用户说"继续实现,看看有什么差距"。把 003 的"尚未实现"、D33–D40 每条的"没做的"和 CubeSandbox 对照里的清单逐条对一遍,挑出不依赖 Rust 重写与 envd 的那些,一轮补上。

**结论**(每项都有单测,节点侧的进了真机套件):
1. **暂停保留期**(003):`retain_paused_s`,暂停后(含空闲自动暂停)保留这么久就删;durable 的暂停时已发 bundle,删了还能导入。密度的另一半:暂停不占内存,但盘上的可写层与内存链要有尽头。
2. **从检查点 fork**(D34):`fork {checkpoint}`,克隆从那个检查点的内存链与可写层副本起,父沙箱不停。Fork 本来就是"从一个 Snapshot 派生",Checkpoint 是 Snapshot,之前只能从"现在"派生是实现上的省事。
3. **WebSocket 端口隧道**(D39):节点握手后把两个 socket 接起来(处理器改成不缓冲读,握手后紧跟的字节不丢);控制面 hijack 客户端连接、拨节点、转发。开发服务器的热更新、终端这类都要它。
4. **出口限额与正则**(D36):每台沙箱 `limits:{requests_per_min, max_bytes}`,超了代理 429 并审计;规则 host 可写 `~正则`。
5. **项目默认网络策略**(D36):`/projects/<p>/network`,创建请求没写 network 就用它。之前每台沙箱自己带策略,项目级的"默认关着 / 只许 pypi"没地方写。
6. **结算账本**(D33):`POST …/statements {from,to}` 把一段时间的账单冻成一行,重叠拒绝;CSV 导出。账单的"算出来"和"结过了"分开,价格后来改了也不影响已结算的。
7. **层分发**(D37):`POST /layers/<id>/everywhere`:从有的节点导出 GNU sparse tar,导入到没有的,id 不变。模板一直能分发,层不能,放置时就被钉在建层的节点上。
8. **节点余量与内存感知负载**(D38):注册节点可带 `reserve_vms` / `reserve_mem_mib`;负载 = 空位占用比与内存占用比里大的那个,balance 与 LeastLoaded 都按它。
9. **Agent 服务带项目**(D33):`INTAKE_PROJECT` → 创建沙箱带 `project`,用量与配额落在它上,不再都进 default。

**顺带修的**:镜像成层叠在 merged /usr 的 base 上时,镜像的真目录 `/bin` 会盖掉 base 的 `/bin -> usr/bin` 链接,现在先折进链接目标再按 base 文件表剪(第 6 轮);沙箱里 `python -m http.server` 绑定时反查 DNS 在无解析的沙箱里挂几分钟,测试换成 TCPServer——真用户的服务若也反查会一样,记下来。

**没做的**:卷不进 bundle(检查点同日补进去了);优先级抢占只做了「暂停让内存」这一半(VM 位不让,ephemeral 不杀);E2B 的 envd / 模板构建(envVars 做了:spec.env 进每次 exec);泛域名 TLS;出口规则变更的审批流;对象存储后端;Rust 节点代理。

**可推翻条件**:若实际没人用 retain_paused_s 而全靠 ttl_max_s,保留期可以并回去;若层分发的 tar 在大层上太慢(几 GiB),改走分块仓库(fc-store)而不是 HTTP 整体传。

## D42. 再补一轮:卷随迁移走、抢占补齐、放宽审批、沙箱页(2026-11-03)

**背景**:D41 之后用户说"继续做"。剩下的里挑不靠 Rust / envd 的。

**结论**:
1. **卷随迁移走**(D35 的"没做的"):migrate 先把沙箱附着的卷按同 id 导到目标(节点 `/volumes/<id>/export|import`,sparse tar),再搬沙箱;卷还被别人附着就 409、什么都不动;半途失败回滚已搬的记录。接管(evacuate)仍不带卷——节点死了,卷在它的盘上;要活过节点死,卷得走对象存储,那是另一条路。
2. **抢占的另一半**:暂停让不出 VM 位时,结束一台 ephemeral 的 background / batch 沙箱;persistent 只暂停。评测器的 ephemeral 本就可重跑,这是它和 persistent 的根本区别,抢占顺着这条线走。
3. **放宽要审批,收紧立即生效**(003 写了很久的一句):成员的 `PUT /network` 若放宽就落成 Request 等 owner,approve 时才推到节点;`Relaxes` 的定义写在 `network/requests.go`。审批对象留在控制面(沙箱侧的事),工作台的待处理以后从 `/network/requests` 拉,不混进 agent 侧的 Approval。
4. **沙箱详情页**补上检查点(打 / 回滚 / 从这里 fork)、端口地址、卷、环境、限额、保留期。

**没做的**:工作台里的"放宽审批"卡片;接管带卷(要对象存储);抢占不跨项目配额核算(被结束的沙箱不记账);E2B envd / 泛域名 TLS;Rust 节点代理。

## D43. E2B 兼容是入口,自己的 SDK 是正品(2026-11-03)

**背景**:用户问"我们是不是兼容 E2B,并且未来有自己的 SDK"。现状:E2B 的控制面 REST 有了(D40,第二个端口),数据面 envd 没有——拿 E2B 官方 SDK 指过来,建沙箱能成,`commands.run` 不行。我们自己对外只有 CONTRACT 的 HTTP,没有客户端。

**结论**:①先做自己的 SDK(Python,`sdk/python`,零依赖),E2B 有的部分同形(create / commands.run / files / pty / ports / pause / resume / kill / set_timeout),用过 E2B 的人零学习;多出来的是我们的差异:检查点 / 回滚 / 从检查点 fork、预算、工单与 inbox、事件流、卷、构建、账单、项目与放宽审批。②E2B 兼容层保持在"入口"的位置:别人的 agent 零改动至少能建、管、删沙箱;envd 的壳等真有只讲 envd 的接入方卡住再做(D40 的条件不变)。③两层并存不互相要求:走 E2B 进来的拿到和别处一样的执行面,走我们 SDK 进来的多拿一层。

**没做的**:TypeScript SDK;E2B 数据面;SDK 的流式 PTY(现在是 write / read 轮询);泛域名入口。

**可推翻条件**:若前几个接入方全部只用 E2B SDK、不碰我们多出的那层,就该把 envd 壳提前,SDK 退为薄封装。

## D44. 数字与一键部署(2026-11-03)

**背景**:用户要"做成好的产品";和 CubeSandbox 的差距里排最前的是没有数字、没有一键部署。

**结论**:①`ops/bench.py` 量沙箱层:创建(冷 / 热)、exec、暂停 / 恢复、检查点 / 回滚、fork 的 p50 / p95,每台内存(cgroup 增量),密度爬坡;结果与解读在 [benchmark-2026-11](research/benchmark-2026-11.md),每次改了节点侧就重跑一遍、加一节。首批数:冷启 396 ms、**热启 85 ms**(模板快照建一次 1.2 s)、exec 5 ms、检查点 47 ms、回滚 238 ms、fork 328 ms、每台 60–72 MiB(含 guest 触碰页,与 CubeSandbox 的 5 MB 不同口径;pmem 在 lazyfs 挂的 base 上不省),16 台不变慢。②`deploy/docker-compose.yml` 一次起齐全部服务,与 run-node.sh 一一对应、可以混用;密钥经 compose secrets 文件,控制面 / 评测器 / Agent 服务学会 `CP_TOKEN_FILE` / `CP_DB_PASSWORD_FILE`;README 写第一次、升级(drain → 换镜像 → uncordon;SIGTERM 暂停到盘)、备份(只备 db-data / store / secrets)、第二个节点。

## D45. 威胁模型一页、MCP 入口、常备模板快照(2026-11-03)

**背景**:数字与一键部署之后(D44),差距表里剩下能在共享机器上不加负载做的:安全叙事、agent 的入口、热启常备。

**结论**:①[013 威胁模型](013-threat-model.md):资产、信任边界、五类攻击者(沙箱内代码、恶意成员、被攻破的节点、内网上的人、供应链),每条边界的控制与**已知未做**写在一起,残余风险按严重度排(特权节点容器、长期令牌、无限速、审计可改、节点自报用量),最后一节是外人该看哪几个文件。②`cairnbox.mcp`:stdio 的 MCP 服务,12 个工具,零依赖,协议只做工具调用那几条;这是比 E2B 兼容更短的入口——用 Claude Code / Codex 的人一条 `claude mcp add` 就把我们的沙箱当工具。③部署默认 `TEMPLATE_POOL` 一条(512 MiB / 1 vCPU,常备 1 台),热启 85 ms 成为默认体验而不是 bench 里的一行。

**可推翻条件**:若接入方都走 E2B SDK 而不碰 MCP,MCP 服务退为示例;若外部审查推翻了"节点是信任边界内组件"的假设,节点与控制面之间要加签名的用量与 mTLS。

## D46. 把威胁模型里能在控制面做的三条做掉;工作台批出口放宽(2026-11-03)

**背景**:013 列了五条残余风险;其中三条不碰节点、不加负载,当晚就能做。用户说"其他的你继续做"。

**结论**:①令牌可轮换、可过期:`rotate`(owner、admin、本人)发新令牌旧的立刻失效,`expiry` 给寿命,过期 401;members 表加 `expires` 列(ALTER 失败视为已存在)。②控制面限制:请求体上限(默认 512 MiB,413)与非 admin 每令牌每分钟请求数(默认 600,429 + Retry-After);admin 不限,免得运维脚本被自己拦。③审计哈希链:每行 `prev` + `h = sha256(prev ‖ 行)`,副本重启从最后一行接上;`GET /audit/verify` 报第一处断裂;链之前的旧行算 legacy。④`GET /metrics`(Prometheus 文本)。⑤工作台云页顶上多一块"等你批的出口放宽",owner 点批准 / 拒绝(D42 的卡片)。

**没做的**:范围令牌(只许某项目 / 只读);并发上限;审计转发到独立存储;节点自报用量的抽查;特权节点容器(第 1 条)——那条要动 jailer 的能力集,留给专用机器的那一轮。

**可推翻条件**:若速率上限挡住了正常的评测器(它经控制面建几十台沙箱),把评测器的令牌标成 service 角色不限速,而不是放宽默认。

## D47. 多租户控制台,参考 CubeSandbox 的 WebUI(2026-11-03)

**背景**:用户问能不能参考 CubeSandbox 做多租户控制台。看了它的 README:控制台三步——概览(节点就绪、容量)、模板商店 / 模板(就绪状态、版本矩阵与健康检查)、沙箱(从模板建、看实时日志);节点运维在 CubeOps。README 里没有租户、项目、API key、配额、用量、审计这些,它的控制台是单租户运维视角。我们的租户模型(账户 ⊃ 项目 ⊃ 成员,配额、账单、放宽审批)已经在 API 里,缺的是一个按项目看的界面。

**结论**:①把「云」页改成**控制台**:顶栏项目切换(客户端把选中的项目写进 `X-Project`,整站生效),成员在自己账户的项目间切,admin 看全部。②照它的"概览 → 模板 → 沙箱"顺序,但每一屏按项目:概览(节点存活与容量、本项目沙箱、今天花费、等批的放宽、最近的事);项目与成员(邀请、换令牌、有效期、移除,配额与默认网络);账单(结算、CSV);卷;模板与构建(多节点时加一张**分发矩阵**——它的"版本矩阵"在我们这里就是哪台节点有哪个模板 / 层);审计(新加 `GET /audit`,成员只见本账户项目的行)。③沙箱的实时日志它有、我们是终端 / 执行 / 事件流三个右栏,不另做。

**可推翻条件**:若用户都是单人单项目,项目切换和概览的按项目视图是多余的一层,退回原来的四个标签。

## D48. 沙箱云是独立的产品身份,暂不独立成仓库(2026-11-03)

**背景**:用户问"这个是不是需要独立,对标 CubeSandbox"。CubeSandbox 是一个只做执行面的独立产品(自己的仓库、名字、SDK、部署、路线图)。我们的仓库里沙箱云和 agent 层长在一起,README 一直只讲 agent。

**结论**:①**产品身份独立**:沙箱云有自己的名字(Cairn 沙箱云)、README 的上半部、SDK(`cairnbox`)、MCP、E2B 口、compose 部署、CONTRACT §1/§2、威胁模型、数字——一个外部团队不需要知道 agent 层就能用它。②**仓库暂不拆**:接缝只有一道(002),agent 层是沙箱云的第一个也是最重的用户,拆开后每条接口改动都要跨仓库发版;现在团队是一个人,拆仓库只会增加同步成本。目录已经是按产品分的:`cp/ node/ guest/ sdk/ deploy/` 是沙箱云,`aios/ intake/ eval/` 是 agent 层,`web/` 两边共用(插件按页分)。③**拆的条件**:有了外部贡献者或第二个使用沙箱云的产品,或者两边发版节奏不同(沙箱云要稳定版本号与兼容承诺,agent 层周更)——到那时按上面的目录线拆成两个仓库,sdk 随沙箱云走。④对标 CubeSandbox 的话要分开说:执行面逐项对齐(已做到持平的那些)、他们没有的租户与 agent 面(我们的卖点)、他们有我们没有的(envd、密度数字、模板商店、CubeOps)——README 的"能做什么"表就是这个结构。

**没做的**:独立的版本号与发布说明(现在只有 git 历史和 decisions);英文 README;沙箱云的独立站点 / 文档站。

**可推翻条件**:上面③的任一条成立就拆。

## D50. 故障手册与告警;注册表丢失后能完整重建;不可达不再冒充"不存在"(2026-11-03)

**背景**:差距清单里第 ③ 条:故障手册、指标阈值、容量规划。写手册要逐个故障场景说"会怎样",所以先去读了真实行为——读出来的比预想的糟,有三处当场修了。

**读出来并修掉的**:①**注册表丢了,收养的沙箱落在 default 项目**:控制面对账时只从节点读 class / durable / created / disk,项目、优先级、E2B 元数据全丢,账单与配额会记错账。现在创建时控制面把这三样作为 `labels` 交给节点存着,对账收养时读回(真机演练:删掉一条路由,55 秒后原样回来)。②**不可达冒充"不存在"**:Redis 读失败时按沙箱 id 的请求回 404,Postgres 失败时创建回 404 "no project"——运维会去查项目而不是依赖。现在分别是 503 "registry unavailable" 与 503 "tenancy store unavailable"。③创建时 `RouteSet` 的错误被吞掉:沙箱建出来了但路由没记,现在写审计 `registry_error`,靠对账收养。

**结论**:①`docs/guide/operations.md`:谁保存什么、十个故障场景(每条标依据:测试 / 演练 / 只是读代码)、指标表与告警、备份还原(含一次真实还原演练:79 KB,1 秒,11 张表逐表一致)、容量规划、值班速查。②`/metrics` 补了依赖可达性、计量心跳、响应与限流计数、失联节点上的沙箱数;`deploy/alerts.yml` 十三条规则,单测保证引用的指标都存在、每条都有处置。③**节点失联后不自动接管**写成了设计:没有围栏,分区时两处同时跑同一台沙箱比多等一会儿更糟;靠 `AiosSandboxesStranded` 告警叫人确认后手动 `evacuate`。

**没做的**:fc-store 不可达的故障注入测试(手册里标了"只是读代码");审计日志的自动轮转与 `usage_events` 的保留期(手册里写了手工办法);`store/` 的还原演练;在这个标签机制上线**之前**创建的沙箱仍然收养到 default;自动接管(要先有围栏);审计链校验没有指标(用 cron)。

**可推翻条件**:若多副本部署里发现"最长一分钟的 404"不可接受,把对账的节奏从每分钟改成事件驱动(注册表恢复时立刻对账),或让按 id 的请求在路由缺失时回头问节点。

## D52. fc-store 可以落到 S3 兼容对象存储(Garage)(2026-11-03)

**背景**:用户问"要不要起一个类似 S3 的专用存储服务"。`fc-store` 是单进程 + 本地磁盘:单点、无副本、容量绑在一台机器上,商业化差距清单里的 G3([commercialization-gap](research/commercialization-gap-2026-11.md))。

**结论**:①选 **Garage**(单二进制、一个容器一个 toml、能扩成多副本、镜像在本机受限出口下能拉到;MinIO 的镜像拉不下来)。②**不让节点和控制面直接说 S3**:`imgstore.py` 加了后端抽象(`FsBackend` / `S3Backend`),`fc-store` 对外仍是原来的 HTTP 接口,落地换成桶。回退只是不带 `STORE_BACKEND` 重启。③S3 客户端自己写(标准库 + SigV4,路径风格),不引入 boto3,容器镜像不变。④存储出错回 502 而不是 404;`gc` 与列表走分页;`migrate` 先拷块后拷清单,断了重跑即可。⑤测试:两种后端跑同一个场景;S3 先对进程内假服务跑,设 `S3_ENDPOINT` 时对真实桶再跑一遍(在盒子上对真实 Garage 通过)。

**没做的**:多节点 Garage 与副本(单节点仍是单点);桶级别的生命周期与版本;把节点的懒加载读直接指向 S3 预签名 URL(省一跳,先量再定);`store/` 与 `s3/` 的还原演练。

**可推翻条件**:若 1 MiB 小块的并发读延迟明显差于本地盘,在节点侧加读缓存或回到本地目录作热层;若许可证(Garage 为 AGPLv3)成为对外分发的障碍,换 SeaweedFS 或自管 MinIO 构建。

## D53. 账户停用:滥用处置的第一块砖(2026-11-03)

**背景**:商业化差距 G2(滥用治理,[路线](research/commercialization-gap-2026-11.md))。没有"一键停"就没法对陌生租户开放:发现滥用时只能逐个删沙箱,而账户还能继续建。

**结论**:①**账户级**停用(账户是责任主体,项目之间可以互相转移资源,停项目会被绕开)。②停用 = 记下 + 暂停运行中的沙箱(保留现场);成员仍可 `GET/HEAD/DELETE`(看、导数据、清理),其余写操作一律 403,**含 E2B 端口**;部署者不受限。③**拦在入口一处**(`serve` 里身份解出之后、分发之前),不是散在每个 handler 里——新增接口默认也被拦。④状态在 Postgres(`suspensions` 表),每个副本缓存 3 秒;数据库读不到时按"未停用"处理(不因为存储抖动把所有人拒之门外)。⑤reason 必填且对成员可见;审计记 `account_suspend` / `account_unsuspend`;指标 `cairn_accounts_suspended`;控制台顶部红色提示。

**没做的**:自动检测(CPU 持续满载、出口洪泛、异常创建速率)与按规则自动停用——这一步要先有阈值数据,现在只给手动按钮;新账户限额(试用额度);按项目而非账户的停用;停用期间的数据导出配额。

**走查后的修正(同日)**:写 D56 时回头审 D53,发现"成员仍可 GET"有漏洞——节点会在 exec / files / events / ports 这些请求上**透明恢复**暂停的沙箱,连 GET 也一样,所以被停用账户读一次文件就把沙箱恢复了。现在被停用账户只放行列表、单台信息、检查点 / egress / metrics 的 GET 与 DELETE;`viewer` 也不能开 WebSocket(能写的 GET)。同时修了三处:预览 cookie 跳转不再可能被 `//host` 带去别的站点;`X-Forwarded-For` 只在 `CP_TRUST_PROXY=1` 时才信;限速表按键增长有上限(无需登录的 `/signup` 的键由攻击者决定)。

**可推翻条件**:若出现"同一个人开多个账户"的规避,账户级不够,要加按成员 / 来源的封禁;若 3 秒缓存导致停用后仍有请求漏过造成损失,缩短或改成 Redis 发布订阅。

## D54. 节点自我围栏 + 可选的自动接管(2026-11-03)

**背景**:商业化差距 G4。手册 F3 一直写"不会自动接管,因为没有围栏"。围栏通常靠断电 / 管理口,我们没有;但可以反过来让**节点自己**围栏自己。

**结论**:①节点:`FENCE_AFTER_S`>0 时,带令牌的请求(控制面的健康轮询就带)是"控制面还够得着我"的证据;静默超过该时间,节点把 persistent 沙箱暂停到盘(durable 的会发布 bundle)、销毁其余;控制面恢复后围栏解除,但被暂停的沙箱**不自动恢复**(由控制面 / owner 决定)。health 多 `fence_after_s` / `fenced` / `cp_quiet_s`。②控制面:`AUTO_EVACUATE_AFTER_S`>0 时,每 10 秒看一遍,失联超过该时间且这次失联还没处理过的节点自动 evacuate 一次(沿用租约,多副本只有一个做),审计 `auto_evacuate`;从没上线过的节点不管。③**两个数的关系是安全条件**:控制面的窗口必须大于节点的围栏窗口加余量,否则可能在节点还没停下时就开始在别处恢复。compose / run-node 都只透传环境变量,默认都是 0(关)。

**没做的**:在真实网络分区上演练(需要能切断一台机器网络,共享盒子上不做);围栏时存储也不可达的情况下 bundle 不是最新的(手册已写);卷不带(仍在死节点的盘上);自动接管后的"回切"。

**可推翻条件**:若控制面自身故障频繁到让节点误围栏(静默 ≠ 节点所在网络断),改成节点同时探测一个第三方见证(如注册表 Redis)再决定;若误围栏造成损失,把默认窗口放大或保持关闭。

## D55. 预览域名:`<端口>-<沙箱>.<域名>` 直接在浏览器里打开沙箱的服务(2026-11-03)

**背景**:商业化差距 G7。现在沙箱里的 web 服务只能用 `/sandboxes/<id>/ports/<port>/…` 加 bearer 头访问,浏览器直接打开不行(页面自己的子请求带不了头),也不能给别人一个链接看。

**结论**:①`PREVIEW_DOMAIN` 设了才启用:`8080-sb-1a2b.<域名>` 在入口被改写成 `/sandboxes/sb-1a2b/ports/8080/…`,其余逻辑(鉴权、项目隔离、账户停用、转发、WebSocket 隧道)**原样复用**,没有第二套代码路径。②凭证放 cookie:带 `?token=…` 的第一次 GET 设 `cairn_preview`(HttpOnly、SameSite=Lax,经 TLS 终止时带 Secure)并 302 去掉 token,token 不留在地址栏与 Referer 里;之后同域的所有子请求自动带 cookie。③转给沙箱里应用的 `Cookie` 头会去掉我们的凭证。④域名与通配 DNS / 证书是部署者的事(前面放 Caddy / nginx 终止 TLS);我们只认 Host。

**没做的**:公开(免 token)的预览链接——要有每端口的开关与过期,否则等于把沙箱服务暴露在公网;cookie 用的是**成员令牌本身**(有效期同令牌),更稳的做法是签发短期的、只对这个沙箱这个端口有效的预览令牌(要等命名 API 密钥那一期);按预览流量计量;自定义域名。

**可推翻条件**:若浏览器把 `<port>-<id>.<域名>` 当成同站点导致 cookie 串到别的预览(同一父域下的不同沙箱会共享不到 cookie,因为 cookie 没设 Domain,但要在真实域名上验证),改成每个沙箱一个随机子域加一次性换取。

## D56. 命名 API 密钥与只读角色(2026-11-03)

**背景**:商业化差距 G9。CI 和看板只能拿某个人的成员令牌,人走了要换令牌、权限也给多了;没有只读角色。

**结论**:①**密钥**是独立于成员的凭证(`api_keys` 表,只存哈希,`cairn_` 前缀便于扫描泄漏),**绑定一个项目**,角色只有 `member` 或 `viewer`——**没有 owner 密钥**,也不能用密钥再发密钥(创建者不能授予自己没有的东西,同 Daytona)。②解出身份时多一个 `Project` 字段:`ResolveProject` 对密钥只认这一个项目;`canSee`、账户范围、E2B 端口的范围都收窄到它。③`viewer` 拦在入口一处(同 D53 的停用拦截点):非 GET / HEAD 一律 403;E2B 端口同样。④`last_used` 每分钟最多写一次(每个请求写库不值得)。⑤控制台"成员与密钥"页加了密钥区:创建(名称 / 权限 / 有效天数)、列表、撤销,secret 只显示一次;两个 SDK 加了 `keys / create_key / revoke_key`。

**没做的**:按操作的细粒度范围(只能建沙箱、只能读账单);billing 角色(只读账单);密钥的来源 IP 限制;泄漏扫描回调;把预览 cookie 换成由密钥签发的短期预览令牌(D55 的遗留)。

**可推翻条件**:若客户要的是"只能做某几件事"而不只是读写,上范围(scope)列表而不是加更多角色;若密钥数量大到 Resolve 多一次查询成了热点,给解析加短期缓存(撤销的延迟就变成缓存时长,要写进文档)。

## D57. 沙箱实时指标:节点侧环形缓冲 + 控制台折线图(2026-11-03)

**背景**:商业化差距 G8(可观测)。控制台的"指标"页只有此刻的读数,客户排查"为什么慢 / 为什么被杀"没有曲线可看。

**结论**:①**节点**每 5 秒读一次沙箱 cgroup 的 `cpu.stat` 与 `memory.current`(jailer 已经建好,不用新探针),加上出站累计字节,放在进程内的环形缓冲(720 点 = 1 小时,环境变量可调)。②`GET /sandboxes/<id>/metrics?since=` 由节点直接答;控制面本来就把 `/sandboxes/<id>/…` 原样转发,**控制面零改动**,权限与项目隔离沿用沙箱路径的检查。③控制台"指标"页:CPU(上限线 = vCPU×100%)、内存(上限线 = 配额)、出站速率,5 秒刷新;老节点没有这个接口时页面如实说明,不报错。④图是 80 行的 SVG 组件,不引图表库(依赖少、深浅色靠令牌自动跟随)。

**没做的**:跨重启持久化(要不要落盘看客户是否要历史);项目级聚合与按标签拆分(要控制面采集,是 P2 用量页的活);磁盘 IO 与进程数;告警(基于曲线的阈值通知);盒子上还没升级节点镜像,所以真实沙箱上这页还会显示"没有实时指标"——升级节点要重启节点容器,属于需要你点头的操作。

**可推翻条件**:若沙箱数上千后每 5 秒遍历 cgroup 成了节点 CPU 负担,改成按需采样(有人看这页时才采)或把间隔放大到 15 秒。

## D58. 滥用检测:只标记,不自动处置(2026-11-03)

**背景**:D53 给了手动停用按钮,但谁该被停还得靠人去发现。商业化差距 G2 的另一半。

**结论**:①利用 D57 的节点指标:控制面每分钟对运行中的沙箱取最近 10 分钟的点,**平均 CPU ≥ 分到的 vCPU 的 90%** 或**平均出站 ≥ 阈值**就出一个信号;样本不足(窗口覆盖 < 80%)不判,同一沙箱同一种信号 30 分钟内只标一次。②信号去三处:审计 `abuse_signal`、指标 `cairn_abuse_signals_total{kind}`(告警 `AiosAbuseSignal`)、`GET /abuse/signals`(仅部署者)。③**不自动停**:编译、训练、评测都会合法地满载;误停一个付费客户的代价大于晚几分钟停一个矿工。自动处置要等有了真实流量上的误报率再谈。④判定是纯函数加一个 `Source` 接口,单测用假数据覆盖(满载标记、合法负载不标、年轻沙箱不判、不重复标记、出站速率)。

**没做的**:自动暂停 / 停用;按账户聚合(一个账户开十个半满载的沙箱);对出站目的地的异常判断(访问矿池域名之类——出口审计里有数据,还没拿来用);用户可见的"你的沙箱被标记了"的通知;阈值按模板或套餐调整。

**可推翻条件**:若上线后误报多到值班的人开始忽略告警,先按账户 / 模板放宽阈值,而不是关掉;若出现"每个都不满载但总量很大"的规避,改成账户级聚合。

## D59. 预付额度:账本、零额度即停用、充值即恢复(2026-11-03)

**背景**:商业化差距 G6(收款)。有计量与账单,但钱怎么进来、钱用完怎么办都没有。

**结论**:①**账本**(`credits` 表,只追加):充值为正,调整 / 退款为负;余额 = 账本之和 − 账户所有项目的累计 `usage_events` 成本——不另存余额,所以不会和用量对不上。②**每账户可选预付**(`account_billing`),默认后付,**现有账户行为不变**。③预付账户余额 ≤ 0:创建 402 `quota: out of credit`;巡检(每分钟)把账户**停用**——复用 D53 的机制(暂停、只读、成员能看到原因),不另造一套"欠费状态";充值**立刻**触发一次巡检并解除这种停用,别的原因的停用不受影响。④**支付服务商不进控制面**:Stripe 之类的 webhook 在一个独立的小服务里验签后调 `POST /accounts/<a>/credit`,支付密钥不进控制面;这个接口只给部署者。⑤数据库读不到时余额按"充足"算,不因存储抖动拒绝客户。

**没做的**:支付服务商对接本身(要真实的账号与密钥);发票与税;余额不足的提前提醒(邮件 / webhook);套餐(月费 + 包含额度);免费额度与试用;按日 / 按月预算以外的限额联动;并发下的轻微超支(余额在两次巡检之间可能为负,最多一分钟的用量)。

**可推翻条件**:若客户要的是月结后付 + 信用额度而不是预付,把 `credits` 当作"信用额度调整"用,阈值从 0 改成 −额度;若一分钟的超支窗口不可接受,把巡检缩短或在 `Record` 里同步检查。

## D60. 邀请制自助开户(2026-11-03)

**背景**:商业化差距 G2(注册风控)与 G10(开通)。账户只能由部署者手工建,内测放人进来要人工;而完全开放注册又没有风控。

**结论**:①**邀请码**是唯一的入口:部署者发一次性码(只存哈希,带有效期),码里带新账户的起点——初始额度(同时转成预付,D59)、并发与日预算配额(试用限额)。②`POST /signup` 是**唯一不要 bearer 的写接口**:凭码创建账户和 owner,令牌只返回一次;码的认领是一条 `UPDATE`(两人抢同一个码只有一个成功);名字冲突时把码放回去,让人换名字重试。③所有关于"码"的失败长得一样(403),不让人探测有效码;按来源地址每分钟 10 次的限速(经反向代理时认 `X-Forwarded-For`,可伪造但只会放宽限速,真正的门是码)。④控制台登录页加了入口。⑤**不做邮箱验证**:邀请制下码本身就是身份凭证,发码给谁是部署者的事。

**没做的**:公开注册(无码)——要邮箱 / 手机验证、验证码防机器人、更严的新账户限额;邀请码撤销接口(现在靠有效期);按邀请码统计转化;账户删除与数据导出。

**可推翻条件**:若要开放注册,把"邀请码"换成"邮箱验证后自动发码",其余(试用额度、预付、限额、检测)原样可用;若邀请码在群里被转发滥用,给码加使用次数上限与绑定邮箱域名。

## D61. 公开状态接口与状态页(2026-11-03)

**背景**:商业化差距 G10(信任)。客户碰到问题先问"是你们挂了还是我的问题",现在没有可以指给他们看的地方;`/health` 含节点名与错误文本,不能公开。

**结论**:①`GET /status` 公开、粗粒度、只有五个通用组件(接口、注册表、数据库、存储、沙箱)和三个状态;**503 表示 outage**,外部探活器(UptimeRobot 之类)直接按状态码判断。②判定只用控制面已有的依赖探测(同 `cairn_dependency_up`)和节点存活数,没有新探针;节点名、主机、错误文本一律不出现(测试里断言)。③控制台的 `/console/status/` 是免登录页面,读同一个接口。

**没做的**:历史(过去 90 天的可用率、事件时间线)——需要把状态采样存下来,并且要有人写事件说明;订阅通知;按地区;状态页自身不依赖控制面(控制面挂了这页也打不开——对外要把它放在独立的静态托管上轮询这个接口,或用第三方探活服务)。

**可推翻条件**:若客户要 SLA 数字,要从指标(`cairn_dependency_up`)算可用率,而不是靠状态页截图。

## D62. 控制面 ↔ 节点可选 TLS(2026-11-03)

**背景**:威胁模型 T8:控制面到节点这一跳明文,上面跑着节点令牌和沙箱的内容(文件、命令输出)。同机 docker 网络可接受,跨机不行——而商业化意味着多机。

**结论**:①**节点**:`TLS_CERT` / `TLS_KEY` 设了就在原端口讲 HTTPS(TLS ≥ 1.2),没设行为不变。②**控制面**:节点 URL 是 `https://` 时用 `NODE_CA_FILE` 里的 CA 校验(没设用系统根证书);普通请求和 WebSocket 隧道走同一份信任配置;`http://` 的节点不受影响,所以可以逐台迁移。③`deploy/tls/gen-certs.sh` 给小部署做一个自建 CA 和每节点证书(主机名进 SAN)。④不做双向 TLS:节点身份靠证书,控制面身份仍靠节点令牌——令牌现在在加密信道里了。⑤测试:节点用生成的证书起 HTTPS、信任它的客户端通、不信任的被拒;控制面用 `httptest` 的 TLS 服务验证"未信任被拒、加入 CA 后通"。

**没做的**:证书自动签发与轮换(现在手工,一年期);双向 TLS;节点 → fc-store / 模型代理 / 注册表等其它内网跳;在真实跨机环境验证(只在单机上测过);控制面热重载 CA。

**可推翻条件**:若证书过期成了常见事故,要么引入 ACME / 内部 CA 自动签发,要么改用 WireGuard 做整条内网加密,TLS 退回可选。

## D63. 命令行 `aios`(2026-11-03)

**背景**:商业化差距 G7(接入面)。E2B、Daytona 都有 CLI;现在想"看一眼有哪些沙箱、进去跑条命令、拷个文件"只能写 Python 或手拼 curl。

**结论**:①CLI 放在 Python SDK 包里(`aios = cairnbox.cli:main`),零依赖,**只是 SDK 的一层薄壳**——没有第二份 API 知识:`ls / create / exec / pause / resume / rm / cp / checkpoint / rollback / keys / usage / whoami / status`。②`exec` 的退出码就是命令的退出码(能进脚本);错误一行信息、退出 1;`status` 不要令牌,中断时退出 2(可当探活)。③`cp` 用 `sandbox:/路径` 语法,只有一边是沙箱。④测试复用 SDK 的假控制面。

**没做的**:交互式 `shell`(要 WebSocket / PTY 终端);`logs -f`;从 Dockerfile 构建模板(`cairn build`,要把上下文打成 tar 上传到 `/builds/archive`——接口有,CLI 还没包);shell 补全;单文件二进制分发(现在要先有 Python)。

**可推翻条件**:若用户主要是前端 / Node 团队,给 JS SDK 做同样的 `npx cairnbox` 入口,而不是让他们装 Python。

## D64. 构建日志与运维账户页(2026-11-03)

**背景**:商业化差距 G8 的后半(构建日志),以及"我是运维,这些新接口我在哪点":D53–D60 加的停用、充值、邀请码、滥用信号都只有 API。

**结论**:①**构建日志**:节点在拉 OCI 镜像时按步骤记进度行(带秒数),放内存里一小时;控制面把构建 id 传给节点,`GET /builds/<id>/log?since=` 转发读取,权限同构建本身(能看构建才能看日志);控制台构建表里的"构建日志"按钮,进行中每 2 秒刷新;两个 SDK 加了 `builds.log`。②**运维账户页**(`/console/admin/`,仅 operator):账户列表(状态、预付 / 余额)带停用 / 解除 / 充值 / 切计费方式,邀请码的创建与列表(码只显示一次),滥用信号表——全部是已有的部署者接口,页面只是把它们放在一处。

**没做的**:`commit` 与 `archive` 构建的日志(它们是单步操作,没有可记的过程);日志落盘或进审计(现在重启即丢);构建失败时把日志末尾直接放进 `error`;运维账户页没有截图(截它要把 admin 令牌放进浏览器,不做)——页面经 `tsc`、构建与单测,但**没有在浏览器里走过**。

**可推翻条件**:若客户要排查一小时之前的构建,把日志写进 `builds` 表(CP 定期拉取节点的行并落库)。



## D65. 默认价目表对齐竞品公开价(2026-11-03)

## D67. 可选的"活跃 CPU"计费口径(2026-11-03)

**背景**:[定价对照](research/pricing-2026-11.md)里 Vercel 按活跃 CPU 计费而不是按分配;agent 沙箱大部分时间在等模型回复,这种口径对客户便宜得多,也是我们能做而按分配计的竞品做不到的差异点——D57 之后节点已经读着 cgroup。

**结论**:①节点在沙箱信息里加 `cpu_usec`(客户机 cgroup 的累计 CPU 微秒,只在 jailer 里运行时有)。②计量巡检里,价目表里 `vcpu_active_s` 的价 > 0 才处理:取与游标的差记成事件;游标回退按"重置"算(暂停恢复重建 cgroup);计量第一次看见一台已经跑了 5 分钟以上的沙箱时只建基线,不补收。**价为 0(默认)时一行都不记**,所以不改变任何现有账单。③分配口径与活跃口径可以并存也可以二选一(把 `vcpu_s` 价设 0)。

**没做的**:活跃口径下的内存(内存是占着的,一般仍按分配);单价建议(缺真实负载数据);控制台里按口径对比"如果按活跃计你会少付多少"的提示——这对说服客户很有用。

**可推翻条件**:若真实负载下活跃 CPU 与分配 CPU 之比接近 1(都在满载),这个口径没有意义,保留代码但不推广;若 cgroup 计数在某些宿主上不准(嵌套 cgroup / cpu.max 限速),退回按节点自报。

## D68. 账户下线与整条客户旅程的真机演练(2026-11-03)

**背景**:①账户只能建不能删——没有下线,GDPR 式的删除请求和测试清理都做不了。②单元测试各管一段,没有一个脚本把"邀请 → 开户 → 密钥 → 沙箱 → 额度用完 → 停用 → 充值 → 下线"在真实控制面(Postgres、真节点)上串起来走一遍。

**结论**:①`DELETE /accounts/<a>`(仅部署者):有沙箱或卷时 409,`?force=1` 连它们一起删;删成员、密钥、项目、配额、停用与计费记录;**保留账目证据**(用量、账本、结算、审计);**账户名保留不再发放**,因为账本与用量按名字记,新账户会继承旧账户的余额。②`ops/journey.py`:把上面那条旅程写成脚本(17 步,不打印令牌,结束时删掉自己建的账户),在开发机的控制面上跑。③运维账户页加了"删除账户"(要输入账户名确认)。

**没做的**:数据导出(下线前给客户一份他们的数据);软删除与宽限期(现在是立刻);删除时对节点上该账户的模板 / 层的清理。

**可推翻条件**:若客户要求"删除后可恢复一段时间",把账户先标成 `deleted` 并停用,N 天后再物理删除。

## D69. 一步做出模板:`templates.build()` 与 `cairn build`(2026-11-03)

**背景**:商业化差距 G7(模板的开发体验)。E2B / Daytona 的核心体验是"写个 Dockerfile 就得到一个预热的模板";我们的路线(镜像 → 层 → 沙箱 → 提交)是对的,但教程要三步手工拼,没人愿意。

**结论**:①SDK 层的一个函数把现有原语串起来:OCI 镜像成层 → 用它起沙箱 → 写文件、逐条执行命令(任何一条非 0 就中止并带出输出)→ 提交成模板 → **无论成败都删掉准备沙箱**。②命令行 `cairn build <名字> --from <镜像> --run <命令>… --allow <域名>… --file 本地:远端…`。③**没有改控制面**:这是客户端编排,所有权限、配额、审计走原来的路径(准备沙箱算在调用者的项目里,占并发配额)。

**没做的**:真正的 Dockerfile 语法(`RUN` / `COPY` / `ENV` 的解析与分层缓存——要一个构建器);构建日志流式回显到 CLI(现在是步骤级的进度行,安装命令的输出在命令结束时一次性给);JS SDK 的同名封装;从一个已有模板增量构建;失败时保留准备沙箱供排查(现在一律删除)。

**可推翻条件**:若客户大量携带现成的 Dockerfile,就要在节点上放一个 BuildKit 并加 `kind: dockerfile` 的构建,这个客户端编排保留为"没有 Docker 构建器时的退路"。

## D70. 沙箱列表的过滤与分页(2026-11-03)

**背景**:`GET /sandboxes` 一直是"全部",租户有几百上千台沙箱时,控制台和脚本都在客户端过滤——每次拉回所有,也没法"只要 team=red 的"。E2B 有 metadata 查询与分页,是客户自动化里最常用的两个。

**结论**:`?status=`、`?metadata=k:v`(多个都满足)、`?q=`、`?limit=` / `?offset=`,响应加 `total`;**不带参数时行为不变**(含顺序);两个 SDK 的 `list()` 接受同名参数。

**没做的**:游标分页(offset 在列表变动时会漏 / 重,对"拉一遍做统计"够用、对"边拉边删"不够);服务端排序字段选择;过滤后仍是向每个节点扇出再在控制面过滤——沙箱量上千后要把过滤下推到节点或建索引;控制台列表页还在客户端过滤。

**可推翻条件**:若单个项目的沙箱数常超过几千,改成控制面维护一份沙箱索引(路由表里已有项目与 metadata),列表直接查索引而不是问节点。

## D71. 创建时的 `start_cmd`(2026-11-03)

**背景**:要"开一台沙箱跑一个 web 服务"得先 create、再 exec 一条 nohup 命令、再自己处理引号与日志——每个客户都在写同样三行。E2B 模板有 start command。

**结论**:`start_cmd` 是控制面理解的创建参数(**不传给节点**):沙箱建好、路由登记后,用节点的 exec 在后台启动一次(`nohup sh -c '…' > /home/agent/start.log 2>&1 &`,命令里的单引号安全转义),响应带 `start`(pid 与日志路径,或失败原因,并审计 `start_cmd` / `start_cmd_failed`)。**启动失败不让创建失败**。不在恢复 / 迁移后重跑(进程在内存里,暂停保留它)。

**没做的**:模板级别的启动命令(提交模板时一并记住,从模板热启动时本来就带着进程,所以暂时不需要);就绪探针(等端口通了再返回);启动命令的重启策略(进程死了不会拉起来);以 root 运行的选项。

**可推翻条件**:若客户要的是"进程崩了自动拉起"和健康检查,那是一个小的进程管理器放进 guest(sandboxd 里),不是在控制面里加参数。

## D72. Webhooks:项目事件的签名推送,带 SSRF 防护(2026-11-03)

**背景**:商业化差距 G8 的最后一项。客户想"建好沙箱 / 构建结束 / 等我批准 / 账户被停了"时被通知,而不是每隔几秒轮询。之前没做,是因为控制面在部署者的内网里,让它替客户去请求任意 URL 就是 SSRF。

**结论**:①**事件来自审计日志**:审计日志加了一个 `Tap`(写完一行后给观察者一份拷贝),webhook 派发器把其中的几类行映射成公开事件(`sandbox.created`、`network.approval_requested`、`build.finished`、`account.*`、`ping`),控制面其余代码**零改动**。②**SSRF 防护在连接时**:拨号器的 `Control` 钩子在 DNS 之后、连接之前检查实际 IP,拒绝私网 / 回环 / 链路本地 / CGNAT / 多播 / 保留地址,所以"指向内网的域名"和 DNS 重绑定都过不了;只收 https、不收 URL 里的密码、不跟重定向;注册时的 URL 检查只是给用户早点报错。测试里有一个**生产模式的拨号器真的连不上回环服务器**的用例。③**签名**:`X-Cairn-Signature: sha256=HMAC-SHA256(secret, 原始体)`,密钥只返回一次;重试 3 次(0 / 5 / 30 秒),连续 10 次失败自动关闭。④仅 owner 管理;每项目 20 个;队列 1024 条满了就丢,**不拖慢控制面**。

**没做的**:至少一次的持久队列(现在重启就丢在途事件);按事件重放;控制台界面;更多事件(沙箱失败 / 暂停来自节点审计而不是控制面审计,要先把它们接上来);多副本下同一事件只投一次靠"谁写审计谁投递",副本之间不去重也没有重复。

**可推翻条件**:若客户要把 webhook 当唯一事件来源,就得有持久队列和重放,要把派发器的队列落库;若需要出站走固定出口 IP(客户的防火墙白名单),要把拨号器放到一个专用出站代理后面。

## D73. 依赖漏洞扫描与升级(2026-11-03)

**背景**:商业化前该做的卫生检查。之前没有任何依赖漏洞扫描。

**结论**:①`govulncheck ./...` 在控制面上查出 **14 个会被我们的代码调用到的漏洞**:`pgx/v5` 5.7.2(GO-2026-5004,SQL 参数转义)、`go-redis/v9` 9.7.0(GO-2025-3540,连接建立超时时回复错位)、`golang.org/x/text` 0.21.0(两条),其余是本地 Go 1.27.0 标准库的(net/http、crypto/tls、crypto/x509 等,在更新的补丁版本里已修)。②升级 `pgx` 到 5.9.2、`go-redis` 到 9.7.3、`x/text` 到 0.41.0;**这要求 Go ≥ 1.25**,于是 `go.mod` 的 `go` 行与构建镜像 `cp/Dockerfile` 一起从 1.23 升到 1.25 / `golang:1.26-alpine`(盒子上拉得到,Go 1.26.10)。升级后控制面全部单测通过,再扫模块类漏洞为 0。③`npm audit` 对控制台和 JS SDK 都是 0 个。

**可推翻条件**:若有可用的出口,把 `govulncheck` 和 `npm audit` 放进 CI 且设为失败即红;在那之前,上线前和每个月手工跑一次(见"上生产"一页)。

## D74. 自己的开发回路搬进沙箱:`dev-go` 模板(2026-11-04)

**背景**:商业化前先自己用。以前改完代码要 tar 到盒子、起 golang 容器和 Postgres 容器跑测试,占用共享盒子,也不计量。

**可推翻条件**:若一周使用里 Postgres 快照恢复出过不健康的实例,模板里就不该带运行中的数据库,改成出生后再启动。

## D75. 修自己用出来的缺口:模板删除、按模板补全配置(2026-11-04)

**背景**:D74 的实验暴露了 5 个缺口,这条处理其中能热修的。

**结论**:①控制面新增 `DELETE /templates/<名字>`:从所有活节点删掉模板和它在存储里的包;admin 可删任何,成员只能删自己项目提交完成的(模板是全局名字,没有单独的所有者字段,所以用"谁提交的构建"判断)。SDK 加 `templates.delete`。②节点在 `new_spec` 里,对 `template_key` 指向的命名模板补全调用方没写的 `template/vcpu/mem/layers/pmem_base/balloon/disk`;写了的照旧必须一致。③打包层过大时,节点把 `No space left` 换成"沙箱 mem 要约两倍于层"的提示。④基础镜像构建写 `/etc/hosts`(localhost)。⑤`ops/dogfood-devloop.py` 提交前等 free-page-reporting 回收,模板内存 1640→906 MiB。

## D76. 并排重建基础镜像:`debian-13-v2`(2026-11-04)

**背景**:D75 留下两个要改 guest 的缺口:基础镜像没有 `localhost`;`pack` 把整层 tar 到 `/run`(内存的一半),大层装不下。

**结论**:①guest 运行时 `pack` 先写 `/run`,遇到空间不足改写根盘 `/var/tmp/pack.tar`(受沙箱磁盘限制),并按名字排除这个文件,否则 overlay 下 tar 认不出自己的归档,会把它也打进层里(第一次试就中招:层大了一倍);节点按返回的路径删除暂存文件。②基础镜像构建写 `/etc/hosts`。③**并排**新建 `debian-13-v2`(新的运行时、新的基础镜像文件 `base-debian-13-v2.ext4`),旧的 `debian-13` 原样保留——基础镜像指纹在模板快照键里,原地替换会让所有快照和暂停的沙箱作废。④实测:新基础上 `localhost` 可解析;1 GiB 内存的沙箱写 800 MB 后 `pack` 成功,tar 838 MB,26 秒;`dev-go-v2` 模板(叠同样的层)上 Go 测试全过。⑤步骤写进 `docs/guide/operations.md` 5b。

**没切换**:默认模板仍是 `debian-13`。切换要改 `DEFAULT_TEMPLATE`(节点)和评估器 / Agent 服务的模板环境变量,并把要保留的模板在新基础上重做;这是一个可以回退的配置动作,等你点头。

**没做的**:真正的流式 `pack`(不落盘);出生时间随模板内存增长的根因;对 `debian-13-v2` 跑完整的节点集成测试(只跑了针对本次改动的验证)。

**可推翻条件**:若切换后发现 v2 上某类任务比旧基础慢或出错,按回退步骤改回默认即可,v2 留作对照。

## D77. 检查点 + fork 的实测:什么时候用(2026-11-04)

**背景**:商业化叙事里"带状态的 fork"是和竞品的差异点,但没拿真实负载量过。

**结论**:在我们自己的 Go 套件上(1–1.4 GiB 驻留内存)量了检查点、回滚、fork:检查点 1.3–2.9 s,回滚 3–5 s 且状态完整恢复,fork 每份 2.4–3.2 s,克隆彼此隔离。①**fork 值得用的场景**是任务中途才产生的昂贵状态(实测一次 60.7 s 的重建,fork 3 份只要 9.7 s);②**不值得**:把测试套件分片并行(最慢分片占整套时间,反而慢)、从模板已有的状态扇出(模板出生每个 0.7 s,更便宜)。③fork 与回滚延迟随内存增长,是新缺口 6。脚本 `ops/dogfood-fork.py`,`COLD=1` 复现冷缓存场景。

**没做的**:用 fork 并行试多种实现(需要真正的 agent 驱动,不是脚本);fork 延迟的根因分析;更大内存下的曲线。

**可推翻条件**:若把 fork 压到每份几百毫秒以内,"从模板扇出"与 fork 的取舍要重新看;若 agent 实验里 fork 的并行尝试没有提高成功率,就不该把它当卖点。

## D78. 出口审批与审计的真实任务检验(2026-11-04)

**背景**:出口审批流、凭证注入、哈希链审计是差异点,但只在单测和演示里验证过,没让真任务走过一遍。

**结论**:拿 D73 遗留的手工项(对控制面跑 `govulncheck`)当任务,让项目成员在出口全关的沙箱里完成,deployer 审批。任务完成,审批 2 轮,审计链校验通过,运行过程能还原到"谁申请了什么、谁批准了";但暴露 6 个问题(详见研究文档第 12 节):被拒的错误没有指引、审计不记 exec、批准人标识为 `default`、`network_relax_*` 无 `project`、OOM 只留 137、模板内存与任务不匹配。①本条只记录和修文档(production 指南加上沙箱里跑扫描的做法),不改行为;②这 6 条里 1、4、5 最影响日常使用,2、3 是审计的完整性问题。脚本 `ops/dogfood-egress.py`。

**没做的**:凭证注入的真任务检验;真人审批延迟;审计是否应记录 exec(隐私与完整性的取舍,需要你定)。

**可推翻条件**:若审计要承担合规用途,就必须记录 exec 与文件操作(带脱敏),并把节点出站日志并入哈希链;那时第 12 节的 2 就从"问题"变成"必做"。

## D79. 修 D78 的 1、4、5:被拒有指引、relax 审计带项目、OOM 有提示(2026-11-04)

**背景**:D78 的真实任务暴露 6 个问题,这三个最影响日常使用且都是小改动。

**结论**:①出口代理拒绝时,403 的原因短语写明"哪个主机、被谁的策略拒、怎么申请"(Go 和 curl 都打印原因短语);主机名与沙箱 id 先过滤字符。②`network_relax_*` 三种审计行加 `project`,成员能在 `/audit` 里看到自己项目的申请与决定。③同步 `exec` 退出 137 时,节点到 guest 里找刚发生的内核 OOM 记录,响应加 `oom_killed`、`hint`、`oom`;只在时间窗口内才算。**纠正 D78**:节点自己的审计日志其实记了 exec(命令前 200 字符与退出码);缺的是它不在控制面的哈希链里、按节点分散,不是"没有记录"。

**没做的**:`exec/stream` 与会话 exec 的 OOM 提示;2(审计是否并入 exec,取舍待定)、3(批准人标识 `default`)、6(模板内存与任务不匹配)。

**可推翻条件**:若 agent 不看原因短语而只看状态码,就要把同样的话放进响应体并给 SDK 一个 `network.request(host)`;若 dmesg 在 guest 里不可读(内核配置变化),OOM 提示要改成读 cgroup 的 `memory.events`。

## D80. 审计链记 exec、批准人写 deployer、模板按任意大小冷启动(2026-11-04)

**背景**:D78 剩下的 3 个问题。

**结论**:①**exec 进链**:同步 `exec`、会话 `exec`、文件读写在控制面哈希链里各留一行(流式 exec 只记请求,没有单一的答复可等)。命令行涂黑常见密钥的形状(`Authorization: Bearer …`、`*_TOKEN=…`、`sk-`/`ghp_`/`cairn_` 等)并截成 200 字符,行里有 `project`、`sandbox`、`by`、`exit`、`s`。**这是个取舍**:链变长、命令行进了日志,涂黑不是保证;默认开,`CP_AUDIT_EXEC=0` 关。理由:没有这些,"它做了什么"在审计链里还原不出来,而节点本地日志分散、不防篡改。②**批准人**:审计行里 deployer 令牌写 `deployer`(它的内部用户名 `default` 与默认账户同名,分不出),审批记录同改;成员写用户名。只改审计与审批显示,不改存储里的归属字段。③**模板大小**:模板仍是确切大小的快照;加 `"boot":"cold"` 就用它的基础和层冷启动、大小随你,拒绝时的错误信息把两条路都说出来。

**没做的**:流式 exec 的结果行;文件内容与 exec 输出不记;节点出站日志并入哈希链;把节点本地 exec 日志与控制面链对账。

**可推翻条件**:若审计行量大到拖慢写入或撑爆磁盘,把 exec 行改成采样或只记失败与 root 的;若客户要求不留命令行,默认改关。

## D81. 检查点的合并内存文件缓存:fork 与重复回滚不再重复合并(2026-11-04)

**背景**:实验 2 的缺口 6 说 fork、回滚延迟"随内存增长"。对照测量(`ops/dogfood-rollback.py`,一个 2 GiB 沙箱,三种状态各打检查点)后,真正的原因不是内存本身。

**发现**:这台盒子 `vm.unprivileged_userfaultfd=0` 且 VMM 在 jailer 里无权限,uffd 用不了(`uffd_note` 本来就写了),恢复内存链长于一个文件时只能先**合并成一个文件**,合并量跟链里的数据成正比。旧代码每次恢复都合并一次:回滚一次、fork 的每个克隆各一次。回滚 `prep_s`(合并)1.3 s(空闲)/ 1.9 s(占 1 GiB 内存)/ 4.3 s(写 1 GiB 文件;被释放的页缓存脏页也留在内存差分里);fork 3 份 5.2 / 6.7 / 11.4 s,几乎是 fork 1 份的三倍。

**结论**:每个检查点的合并文件只建一次,放在检查点目录里(`merged.bin`,稀疏文件,删检查点时一起删)。VMM 以 MAP_PRIVATE 映射它,所以回滚和所有克隆可以共用同一个只读文件。实测:fork 3 份 5.2 → 1.6 s、6.7 → 1.5 s、11.4 → 3.9 s;重复回滚的合并耗时为 0,总时间 2.2–3.4 s → 0.9 s(空闲/占内存)。**每个检查点的第一次回滚或 fork 仍付一次合并**。恢复和回滚的响应、节点审计行现在带 `phases`(进程拉起、合并/准备、快照加载、客户机重连、时钟网络修正),下次不用猜。

**剩下的成本**:回滚要整份拷贝可写层(`cp --sparse`,盒子是 ext4,没有 reflink),0.65 s(几乎空)到 2 s(1 GiB 磁盘数据),随磁盘占用线性增长;fork 的克隆各拷一份可写层,也是这个量级,且仍逐个顺序做。

**没做的**:打开 uffd(要把 `vm.unprivileged_userfaultfd` 改成 1 或给 VMM 权限,是主机安全设置,需要你定);检查点创建时顺带预合并(会让创建变慢,换回滚第一次变快);克隆并行恢复;可写层改成写时复制(设备映射快照或 reflink 文件系统)。

**uffd 方案记录(待定,没做)**:盒子内核 5.15、`vm.unprivileged_userfaultfd=0`、`JAIL=1`。节点容器有 `CAP_SYS_PTRACE` 与 `CAP_SYS_ADMIN`,但 jailer 把 VMM 降权并丢掉所有 capability,而 userfaultfd 必须由映射那块内存的 VMM 自己创建,节点代建不了;容器里 `/proc/sys` 只读,该设置是主机全局的。可选:①主机上 `sysctl -w vm.unprivileged_userfaultfd=1` 并写进 `/etc/sysctl.d/`(盒子上所有无权限进程都能创建 userfaultfd,需要 root,我方没有 sudo);②`JAIL=0`(拿隔离换速度,不建议);③不动主机,把首次合并挪到打检查点时(沙箱不暂停,检查点调用多等 1–4 s)。`/dev/userfaultfd` 要内核 ≥ 6.1,这里走不通。倾向③。打开后要验证:`uffd_note` 为 ok、首次回滚 `prep_s` 接近 0、回滚后状态正确、CI 全过;回退只需把设置改回 0 并重启节点。

**可推翻条件**:检查点很多且很大时,每个多占一份合并文件的磁盘(稀疏,约等于内存里被碰过的页),若成为问题,改成只缓存最近用过的几个,或打开 uffd 后去掉缓存。

### D88 E2B 兼容做成真的:envd 协议由 sandboxd 说,官方 SDK 对着 E2B 口通过一致性用例(2026-11-05)

**背景**:D40 只做了控制面 REST,把 envd 记为"不做",可推翻条件是"外部接入方只会讲 envd"。D43 说 E2B 兼容是入口、自己的 SDK 是正品。用户 2026-11-05 要求"尽量兼容 E2B",并提议让 sandboxd 直接兼容 envd。

**取证(P0,读 e2b 2.63.0 的源码并抓请求)推翻了 D40 的两条判断**:①envd 并不要求泛域名:SDK 读 `E2B_SANDBOX_URL`,设了之后对沙箱的所有请求发到这一个地址,每个请求带 `E2b-Sandbox-Id` 头,一个入口按头路由就够。②官方 SDK 说的是 **Connect 的 JSON 编码**(`useBinaryFormat: false`),不是二进制 protobuf,服务端不需要 protobuf 库;明文 `http://` 下是 HTTP/1.1。另:新版 SDK 创建沙箱调 `POST /v2/sandboxes`,D40 的口只有 v1,所以当时的口连创建都对不上新版 SDK。

**结论**:①**envd 的协议做在 sandboxd(`guest/sbx-runtime/src/envd.rs`)里**,听在 vsock 的第二个端口 49983(只认宿主 CID),一连接一请求(`Connection: close`),HTTP/1.1 手写、JSON 用 serde_json,没有新依赖。进程与文件的逻辑在它该在的地方;进程活在虚机内存里,所以**暂停、检查点、回滚、fork 之后 `commands.connect(pid)` 仍是同一个进程**(E2B 没有这条)。②**不放在沙箱网络的 TCP 上**:那样沙箱里任何低权限进程都能连 `localhost:49983` 以任意用户跑命令,绕过降权。走 vsock,宿主才连得上。③节点新增 `/sandboxes/<id>/envd/…` 流式中继(HTTP→vsock 的字节管道,复用端口暴露的隧道工具);控制面在 E2B 口按 `E2b-Sandbox-Id` 头路由,用**绑定到单台沙箱的令牌**(`HMAC(密钥, "envd|"+沙箱 id)`)鉴权,并**解析 `Start` 的首帧写审计**(命令行、cwd、用户),文件请求审计路径,因此数据面没有绕过审计。④控制面补齐:v2 创建/列表(`state`/`metadata` 过滤、分页)/connect、`fork`、快照(对应"提交成模板")、`update_network`(只有 owner/admin,因为这个口没有审批队列)、`get_metrics`。⑤沙箱不存在时按 E2B 代理的行为回 **502 + "was not found"**(SDK 的 `is_running` 靠它);`envdVersion` 报 0.5.7(我们完整实现的最高版本)。⑥创建时的 `envVars` 经新的 `set_env` 操作写进沙箱的 `/run/sandboxd/env.json`,envd 起的进程可见。

**验证**:官方 Python SDK 2.63.0 的 31 条与 npm 包 2.63.0 的 20 条一致性用例全部通过(`ops/e2b-conformance.{py,mjs}`,结果在 `docs/research/e2b-conformance/`),在一台机器、1 个节点、jailer 开的环境;Rust 13 个单测、Go 测试通过;原生 SDK 快速开始 13/13 没有回归。**没验证**:别的 SDK 版本与语言(Go 等)、两台物理机、压力测试。**版本矩阵与一次疏忽**:Python 与 npm 各 6 个 2.x 版本(2.52–2.63)全过;1.x 不支持。跑矩阵时 Python 1.11.1 不认 `E2B_API_URL`,**把演练栈的管理令牌作为 `X-API-Key` 发到了 api.e2b.app**(2 template"(后台轮询与我手动触发的轮询并发,旧响应可能晚到覆盖新的)。改为节点回 "no template" 时排除它换一个节点重试,所有节点都没有就如实报 400 而不是"没有容量"。**没验证**:`apt_install` / `pip_install` / `git_clone` / `from_dockerfile` 等便捷方法(需要放开出口)、多副本下的上传、从外部镜像构建、tags。**同日补**:创建响应的 `domain` 在设了 `PREVIEW_DOMAIN` 时填它,SDK 的 `get_host(port)` 因此得到 D55 预览主机,一致性用例(沙箱里起 perl 小服务)端到端通过。**同日补验证**:2 个节点容器下两套官方 SDK 用例整套重跑(Python 32、npm 20 全过,新增"暂停中直接 `commands.run`"用例);4 台沙箱按负载分到两节点、杀掉持有已暂停沙箱的节点后 evacuate、SDK 照常用;栈本身的延迟(控制面主机上无 SDK 无隧道):`Start` 到结束 p50 8.6 ms,文件 1 KiB 读写约 4 ms,64 MiB 写 290 / 读 670 MB/s,4 台并行 100 条命令无错误。

**局限(写进兼容矩阵)**:没有模板构建 API、`gzip` 上传、`StreamInput`、`/files/compose`;端口 URL 只在设了 `PREVIEW_DOMAIN` 时可用(见同日补充);`watch_dir` 靠 250 ms 轮询;默认用户是 `agent` 不是 root;新建沙箱要用带 envd 的基础镜像,已有模板快照要重建;E2B 的 `timeout` 映射成空闲 ttl;`allow_internet_access` 不带时用 Project 默认出口策略(不是 E2B 的"默认放开")。

**D40/D43 的更正**:D40 "envd 要求泛域名入口"不成立(见上);D43 "E2B 兼容是入口"仍成立,但入口现在是完整的数据面。
