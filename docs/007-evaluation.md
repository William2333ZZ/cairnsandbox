# 007 评测与晋升

本文说明一个 Cairn 候选版本怎样被打分、与父代比较、入档或晋升。它建立在 [002 领域模型](002-domain.md)、[003 沙箱与平台](003-sandbox.md)、[004 沙箱内系统](004-guest.md) 与 [006 执行](006-execution.md) 之上。

评测器在沙箱之外,持有任务集与真值,自己创建并销毁评测沙箱,给结果签名。它只回答一个问题:这个版本把这个用户的事做得更好了吗。

## 任务从哪来

| 来源 | 真值 | 用途 |
| --- | --- | --- |
| 用户项目里挖出的任务:把一个有测试覆盖的功能挖空(保留签名与 docstring),藏起测试做验收;或从带测试的提交还原 | 有 | 演化集、验证集、留出集 |
| 用户交过的事(Ticket 流) | 合并且带测试的 PR:初始工作区 = 基线提交,提示 = Ticket 文本,验收 = PR 带来的测试 | 来源标签 `user`;进该用户的演化集,Update 里"在你的事上好了多少"算的就是它们;未合并的只进任务内循环与改进库 |
| 公开基准(Polyglot、Terminal-Bench 子集) | 有 | 只做回归与外部坐标;小规模验证管线与统计 |

用户的事挖出的任务有四种(`meta.kind`),每一种问的是一件不同的事(D17):

| 种类 | 怎么来 | 问的是 | 评测怎么做 |
| --- | --- | --- | --- |
| plain | 合并且带测试的 PR | 做得对不对 | 提示 = 原请求,验收 = PR 的测试 |
| dependent | 被用户纠正过的工单(005 纠正),其 PR 合并 | 记不记得住用户教的 | `meta.rules` 是当时提炼的规则;跑的时候把规则按 harness 真实使用的措辞(`rules_text`)接在提示后面,就像记忆会交给它的那样;`memory: off` 的批次是对照臂,同一批题不给规则——两臂之差就是记忆的提升,不是上下文变长 |
| obstacle | 问过用户并得到回答的工单(006 该问就问) | 该问的时候问了没、问得准不准 | `meta.blockers` 是当时的问题与回答;提示里没有答案。agent 以 `QUESTION:` 结束就是在问:问题与某个 blocker 的词重合够高(字/词二元组 Dice ≥ 0.2)就用那条回答继续,否则回"没有更多信息,自己判断";重新从头跑,最多答两次,验收的是最后一次的工作区。每次 Run 记 Ask-F1(问的问题里有几成是真障碍 × 真障碍有几成被问到,HiL-Bench):一个不问就猜的版本,隐藏测试过不了,F1 也是 0 批次参数 `ask: v2` 换一段更直白的提问措辞(`ASK_RULE_V2`:缺的是改变做法的决定且仓库里查不到就先问,问一句比猜错一轮评审便宜),同一版本、同一批题,两臂之差就是措辞的作用;产品仍说 `ASK_RULE`,直到 v2 在 Ask-F1 上胜出 |
| long | 做得久的工单(三次以上派工、或累计 10 分钟、或改 6 个以上文件) | 长任务中途断在哪 | 时限放大;验收脚本每个测试文件输出一行 `SUBTASK <文件> <通过比例>`,最后一行 `SCORE` 是通过的测试占比(部分分);Run 记各项,看得出断在哪一段 |

一件事可以同时带规则和 blocker(kind 取 dependent);类别只决定标签与统计分组,规则与 blocker 是否起作用看字段。批次摘要里有 `by_kind`(各类均值)和 `ask`(这批的 Ask-F1),Update 用它们说"在哪类事上好了"。

第一个用户项目是这个平台本身。公开基准里先接的是 Aider 的 Polyglot(Exercism 练习,DGM 的演化集):`eval/import_polyglot.py` 把 Python 轨道的 34 题导成任务集 `polyglot-py`,DGM 的 small 子集标为烟测;其他语言等 env 层有工具链再导。它回答的是"我们的评测器与版本循环在别人用过的题上给出的数字是否合理",不是"产品变好了吗"。第二个外部坐标是 Harness² 用的 WorkBuddy-Bench Code 子集(腾讯,从真实提交反向构造、题面是口头请求、隐藏功能测试):`eval/import_workbuddy.py` 导入其中自带独立验证脚本、不装额外依赖的 54 题为 `workbuddy-code`(生成物不进仓库,从 190 MB 的原始压缩包重建);22 题真实开源仓库要按依赖建 env 层,4 题仓库理解类走打分器,都未导入。它的题面形态与接单层里用户的请求最接近。

## 任务

| 字段 | 含义 |
| --- | --- |
| id、domain | 标识;领域 coding / ops / data / text |
| group | evolve / validate / test;一个任务只属一组;切分按来源标签做,同源不跨组 |
| prompt | 给 agent 的目标文本 |
| init/ | 初始工作区,整目录进沙箱 `/task`;不得含测试、参考解、`.git` 历史 |
| verify/ | 验收脚本与隐藏测试,只在评测器存储;脚本输入工作区路径,最后一行输出 `SCORE <0..1>`,非 0 退出视为 0 分 |
| reference/ | 参考解,覆盖到 init 上应通过验收 |
| timeout_s、allowed_write、smoke | 时限;允许写路径;是否烟测题 |
| 历史通过率、区分力 | 恒为 0 或 1 的任务无区分力,不进比较核心集,只留回归 |

**导入检查**,全部自动,不过的任务标 invalid 不参与评测(批次开始时剔出,记在批次参数的 `skipped_invalid`):参考解通过;no-op(不改动)不通过;同一解验收 3 次一致;时长在限制内;镜像里没有答案载体。带变体输入的验收能检出硬编码特判。

任务集有版本号,修改产生新版本;批次引用具体版本。

## 一次 Run

```
创建 agent 沙箱(ephemeral,closed 网络,层 = 版本的 langs + harness + 任务集的 env)
  → 送入 /task 与提示 → 领模型令牌与预算 → exec harness(Landlock 默认约束)
  → 导出工作区 tar → 拉事件日志 → 销毁
创建验证沙箱(ephemeral,无网络,同 env 层)→ 解开工作区 → 跑 verify.sh → 取 SCORE → 销毁
```

- 成本与 token 来自模型代理的用量接口;时长、退出码、事件来自节点;分数来自验证沙箱。harness 自报的只作参考。**分数量提升**(D23):按测试文件给的部分分里,没动工作区时就通过的文件不算 agent 的功劳——空改动下没有全过的文件才是目标,每个目标按补上的差距计分,原来通过现在坏了的抵掉一个目标;每次运行另存 `raw_score`。成本按缓存命中计价(命中价是未命中价的 1/50,D22),命中的 token 数另记,所以"每次运行花费"反映真实账单而不是把每一步的整段历史都按新输入算。
- 基础设施失败(沙箱起不来、代理故障)单独标记,重试至多 3 次,不计入任务失败。
- 每个 Run 记作弊信号:读取或列举任务目录外的敏感路径;修改验收相关文件或计时函数;访问 `.git`;试图连 daemon socket 或提权;异常网络访问;输出异常膨胀;重复动作循环;分数高于该任务历史 2σ。`__pycache__` 一类产物不算。
- 事件日志(最多 200 条)、轨迹、验证输出尾部随 Run 保存。

## 噪声与比较

- 同一版本每任务重复 k 次,得到任务 × 次的结果矩阵;avg@k、pass@1、pass^k。
- **噪声带 δ**:同一版本两次独立的 k 次评测之间整体分之差的 95% 分位,用每题 k 次结果有放回地各抽 k 次来模拟(早先用半分法,k = 3 时是 1 对 2,把带子估大了近一倍)。只在通过率离开天花板与地板的任务上有意义;顺序是真实任务集 → 种子通过率分布 → 剔除全 0 全 1 → 再测 δ。统计口径改了之后,已完成的批次用 `POST /batches/<id>/restat` 重算,`evolve.py rejudge` 重新裁决。
- 版本比较一律同任务配对:配对差的标准误、二元指标用 McNemar、分级指标用配对 bootstrap。不用非配对方差。
- 不用温度 0;记录模型版本、端点与缓存命中,任一变化即重测基线。评测中禁用整体响应缓存;依赖与记忆固定。
- 基线按(Cairn 版本、任务集版本、模型版本)缓存。没有基线不能比较。

## 级联

| 阶段 | 内容 | 淘汰条件 |
| --- | --- | --- |
| 构建与自检 | 构建候选 harness 层;能编辑代码、能调模型、能写事件 | 任一不过 |
| diff 级 critic | 含任务名、答案、任务特定分支的编辑;触及评测、记录、传播相关代码的改动按篡改分类 | 拒绝或标篡改 |
| 烟测 | 3 到 5 题,每题 2 次(`smoke_k`) | 某题全部运行失败即淘汰,余题计 0;单次失败只是噪声 |
| 核心集 | 有区分力的演化任务,每题 k = 3 | 配对不优于父代 |
| 全集与留出 | 只对位列档案库前二的候选;演化集全集 k = 5,留出集 | 留出退步 |

## 接受与晋升

候选被接受为新的档案节点,须全部满足:

1. 配对提升 > δ,且 bootstrap 95% CI 下界 > 0;
2. 留出集不低于父代;
3. 成本增量满足 ΔC ≤ β0 + β1·ΔS,不允许用数倍成本换几个百分点(`evolve.py`:β0 = 每次运行 1 美分,β1 让每个分点最多买父代成本的 5 倍份额;分数只持平而更贵的不接受);
4. 旧任务不退步;
5. 无作弊告警;
6. 匹配预算的并行采样基线:harness 提升必须也胜过"同样的钱直接多采样"。

噪声带内的候选不晋升,按成本与新颖性入档。

**档案库**是树。每节点保留结果矩阵与 Beta 后验;父代按子树成功率的 Thompson 采样 × 1/(1 + 子代数)抽取,不看自身分数;任务成功向量与已有节点余弦 > 0.95 的候选需 critic 确认实质不同;稳定版终选用后验保守分位(5%)且评测次数 ≥ 5。

挖出来的题的验收脚本不信被评的工作区(D19 ⑫、D21):删掉工作区里所有 `conftest.py`、`pytest.ini`、`tox.ini`、`setup.cfg`、`pyproject.toml`、`sitecustomize.py` 与名字像 pytest 的目录,换上任务自己存的那一份(`verify/_trusted/`,来自给 agent 的起点工作区),隐藏测试放回原位;结果读写在树外的 junit 文件,不读可以被伪造的输出文本;跳过、预期失败的测试留在分母里,不算通过;某个测试文件没产出任何结果算一次失败。导入时工作区取归档里"所有项共有的那一层"的内部(`git archive --prefix=`、托管的 tarball 都是这样),调用方给的路径、任务集名、任务 id 不能逃出任务目录。

**改动清单与回归护栏**(D17):元 agent 每次提案除 `CHANGES.md` 外还要写 `MANIFEST.json`(不进 harness):改了哪个部件(observation / loop / prompt / tools / helper / config)、哪些文件、为什么、依据哪些失败任务、**预计修好哪些任务、可能弄坏哪些**、什么必须保持不变。驱动器只留它能知道的:不在它见过的任务里的 id、diff 没碰的文件都丢掉。比较做完,驱动器把预测按任务摆在结果旁边(`attribute`):实际修好(均分 +0.25 以上)、实际变差(-0.25 以下)、预计命中几道、**没预计到的变差几道**、以及**原来每次都做对、现在不是每次都对**的任务(`lost_stable`)。前者是为了让更新说得出"因为什么、预计与实际差多少";后者是自改进的已知盲区——元 agent 看得见它想修什么,看不见它弄坏了什么(Agentic Harness Engineering 的自我归因里,预测修好比随机准五倍,预测弄坏几乎不准)——所以它进了接受条件:丢掉的稳定通过超过父代稳定通过数的两成(至少容许一道)就不接受,不论均值涨了多少。`evolve.py explain` 把某次迭代的清单与结果印成一段话。

**效率一臂**(D20):上面第 3 条问"多花钱买到了多少分";另一半是"同样的分少花钱"。配对分数差不为负(点估计)、每次运行的花费不超过父代的 75%、且稳定通过没有丢,就接受——没人注意到 harness 变便宜了、也没变差,是它自己变好的最常见的样子。分数涨了的候选仍走原来的门。

**接受的候选回到人的目录**(D29):设了 `EVOLVE_HOME` 时,被接受的版本还会被写成 `<home>/proposals/<版本>/`:config.json 只写与父代不同的那部分(覆盖层语义,字典逐层、列表整体),prompts/、skills/、middleware/、rules/ 下的文件原样,候选删掉的列进 DELETE,PROPOSAL.md 写来源、评测结论、改动说明;harness 代码(agent.py 等)不在目录格式里,只随层走,PROPOSAL.md 列出来。写进去不等于生效,人跑 `python -m aios.home apply <版本>` 才算(004)。反过来,人的目录里 `tasks/<仓库>/<题>/` 由 `ops/home-tasks.py` 导进评测器,成为题集 `home-<用户>-<仓库>`,evolve 可以拿它当 `--taskset`。

**人写的候选**走同一条路(`evolve.py candidate`):critic 读 diff、建层、登记版本、与父代基线比较、同一条接受规则、清单与结果对照、被接受的以更新送到 agent 面前。区别只在提案者——元 agent 或写这个平台的人。这条路的存在是为了不让"平台开发者顺手改一下 harness"成为一个绕过评测的后门。

**晋升**由沙箱外不含 LLM 的晋升控制器执行,只接受评测器签名的结果:把版本标为 stable,成为新沙箱默认;已有沙箱不自动升级。**回滚**把稳定版指回已知良好版本或任一历史稳定版,不影响运行中的沙箱。两者都写审计。

改动类型在需审批列表中(新增工具或 ABI、放宽网络、读用户数据、R3)的,自动条件满足后仍等人。

## 对用户的更新与回退

每次晋升,晋升控制器为每个跟随稳定版的 Agent 生成一条 Update(002),Agent 服务以 say 送进对话,回答四个问题:**改了什么**(迭代记录里的改动说明)、**为什么**(清单里的 why)、**在你的哪些事上好了**(该用户来源标签为 `user` 的任务上的均值变化与置信区间,没有这类任务就说明用的是公开集;按类别列出依赖题、要问才知道的题、做得久的题各自的变化;该问就问的 F1 变化;预计修好几道、实际修好几道、几道变差)、**怎么退回去**(「退回」会回到哪一版、那一版改过什么)。每次运行的花费变化照旧。噪声带内的变化不晋升,也就没有 Update。用户回复"退回"即把 Agent 钉在上一版;钉住的 Agent 不再收到 Update,直到用户解除。

Run 另记一项**说话次数**(终态之外的 say 数,见 006):它不进接受条件,但在 Update 与版本树里和成本并列显示,让"少打扰"可见。

## 改动级别

| 级别 | 可改 | 条件 |
| --- | --- | --- |
| R1 | 文本型组件:提示、护栏、记忆、技能、工具指引、子 agent | 评测器与噪声估计就绪 |
| R2 | 代码型组件:脚本、中间件 | R1 稳定,契约与系统性质检查完备 |
| R3 | runtime、ABI、解释器版本、评测器 | 永远人改 |

## 自动化的版本循环

`eval/evolve.py` 把级联与接受规则串成一次迭代:按子树接受率的 Thompson 抽样选父代(种子 = 评测器默认版本),没有基线就先跑;元 agent 在一台 dev 沙箱里读父代 harness 源码(只读挂载)与失败轨迹,按轮次轮换的方向(观察格式、错误恢复、工作流提示、工具语义、辅助脚本、系统提示)改写到 `/work/harness` 并写 `CHANGES.md`;diff 级 critic 拒绝提到任务、答案、验证路径或触及计量代码的改动;构建沙箱在 langs 层上装候选 harness、自检、打包成层;评测器登记版本并跑级联比较;接受的候选成为新父代,否则入档。所有分数来自评测器,驱动器自己不打分。状态在评测器状态目录的 `evolve.json`。

## 隐藏集

隐藏集不参与任何自动选择,只做阶段性评估;查看需要显式揭示并记录次数;对 agent 永远不可见。
